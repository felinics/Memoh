## 规则的组成部分

每条规则都固定由八块组成：**适用场景 · 规则 · 原因 · 本仓库的实现 · 常见错误 · 边界 · 自查方法 · 保证方式**。

少任何一块，这条规则在实际干活时都会掉链子：没写“适用场景”，写代码时根本想不到要翻这条；没写“原因”，遇到稍微变个形的场景就不知道怎么拿捏；没写“本仓库的实现”，读者就会按自己在别处习惯的野路子去写。

“原因”要写明依据：规则来自外部规范时，给出能定位的出处（文档标题加小节名，或条款号，附链接），来源按 `SKILL.md`「依据来源」的优先级选取，清单见 `sources.md`；规则来自负责人的决定时，写明“负责人确认”和日期。同一条规则既引用了规范、又有意偏离它时，写明偏离点和理由。

## 规则推导方法

当线上或 Review 里抓到一个具体问题、想把它沉淀成一条能防住整类问题的规则时，按下面六步走：

1. **先找它违背了哪条大原则**：回到 `SKILL.md` 的五条原则对号入座。如果哪条都靠不上，说明顶层原则可能有遗漏，先审视原则。
2. **用“用户能感知到的结果”来下定义**：比如写成“看过的页面再次点开时，第一帧直接显示内容”，而不要只写“列表要做缓存”这种具体技术手段——因为导致再次打开空白的原因可能有好几种，只定技术手段会漏掉其他成因。
3. **在“本仓库的实现”里给且只给唯一一条标准路子**：如果只喊口号“大家要做缓存”，最后十个人会写出十套五花八门的本地缓存。
4. **把正确做法做成默认最省事的路子**：尽量把默认值、公共组件（owner）和封装函数（helper）在底层配好，让写业务页面的人不用动脑子选就已经守了规矩。
5. **配套规则一起定**：比如只定“所有读取都要走缓存”，三天后准会出“改了数据列表却不刷新”的 bug；所以“怎么缓存”和“什么时候让缓存失效”必须成对写清楚。
6. **把卡点埋在写代码的必经之路上**：同步放进 `SKILL.md` 索引表和 `review.md` 审查清单；凡是能用脚本写死判断的，直接加进 lint 守卫。

越往后走，需要人死记硬背的文字就越少；最理想的状态是正文只剩一句“直接用某某组件”，剩下的脏活全由那个组件在内部兜住。

**怎么拿捏规则的抽象高度？** 抓到一个具体错误后，连续问自己“这属于哪一类问题？”，往上一层一层提，直到**再往上提一层就会变成正确的废话（比如“体验要好”）、没法直接拿来判别代码对错**为止——停在它的前一层，就是最合适的颗粒度。再挑两三个跨度很大的真实例子放进去帮读者看清边界。

## 保证层级

从最稳到最弱分四档：

1. **结构**：从 API、类型或组件封装上让你根本写不出错误做法（最稳，比如统一走某个 owner 或 helper）。
2. **机械检查**：写错了立刻在 `mise run lint`、UI 契约守卫脚本或测试里报错拦截。
3. 文字：规则正文。
4. **建议**：需要结合上下文拿捏的设计与体验取舍。

每条规则末尾的“保证方式”都如实标着它现在处在哪一档；如果目前还只能靠文字约束、但其实能做成代码或脚本拦截的，会同时标出“目标”档位。只要某条规则成功升级到了“机械检查”或“结构”档，规则文档里的长篇叮嘱就可以相应砍短，同时把拦截脚本的报错提示写清楚（告诉作者违背了哪条规则、该怎么改）。

## 层级提升

只要同一条文字规则在实际开发中被踩中第二次，就不再靠嘴说，直接往上升一档：能写进检查脚本的升为“机械检查”，能收进底层组件的升为“结构”（存量老代码记进 baseline 豁免，新增代码零容忍，baseline 只准减不准增）。

## 单一出处

每条规则只在一处完整说明，其他文档引用时只写一句话并给出链接：两份说明会逐渐
不一致，也会额外占用读者的注意力。发现两份文档重复或互相矛盾时，记录下来并报告
规则负责人，附上建议的处理方式，由负责人决定保留哪一份。

## 保持 skill 可读

- `SKILL.md` 的正文控制在 200 行以内（不含表格），细节放入 `references/`。
- 每个参考文件以目录开头，写明每一节标题所在的行号。修改参考文件后，更新目录，
  并对照最终文件核对每个行号。
- `SKILL.md` 的 `description` 写明哪些任务应加载这个 skill、哪些不应加载；
  范围写得过宽，无关的工作也会加载它。
- `SKILL.md` 的规则索引、`references/review.md` 的条目和
  `references/rules.md` 同步修改：新增、重命名或删除一条规则，三处都要修改。

## 规则修改权限

任何人或 agent 都可以把违规作为事实记入下方记录：日期、规则、经过、位置。新增、
修改或升级规则由前端规则负责人决定，agent 不自行修改。

有人纠正 agent 对某条规则的应用方式，或要求采用与规则冲突的做法时，agent 指出
两者的差异，并确认这是一次性的例外还是长期的变更。一次性的例外只适用于当次情况；
长期的变更作为提议提交给规则负责人。
