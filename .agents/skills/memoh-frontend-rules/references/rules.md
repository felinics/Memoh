## 1. 面向用户的承诺

### U1. 不泄露，不越权

**适用场景：** 显示、缓存、持久化或打印来自服务端、模型、工具、渠道或其他用户的
数据；按权限控制界面控件。

**规则：** 密钥绝不出现在界面、控制台（`console`）或浏览器本地存储中；来自模型、
工具和渠道的内容一律当成不可信输入处理；权限只由服务端拍板校验。

**原因：** 前端露出的密钥很容易通过截图、投屏或导出的 localStorage 泄露。Bot 的输出
也可能被外部内容污染——比如一条渠道消息或 agent 刚抓取的网页里就可能带着恶意 HTML。

**本仓库的实现：**
- 查询缓存会持久化到 localStorage（`lib/query-cache-persistence.ts`）。落盘前，
  `deepStripSecrets` 会剥掉名字像密钥的字段；`EXCLUDED_QUERY_KEY_HEADS` 列出的查询
  key 前缀整条不落盘。新写的查询如果返回凭据，或者返回可能夹带凭据的原始配置字符串
  （比如原始 hook 配置），必须加进这个排除列表。
- 模型、工具和渠道返回的文本一律走 markdown 组件（`components/markdown/`，基于
  markstream-vue）渲染，绝不用 `v-html`。仓库里现有的几处 `v-html` 只用于渲染经过
  Shiki 转义高亮的代码块，并带有行内 eslint 豁免注释。
- `meta.adminOnly` 路由守卫和按权限隐藏入口（比如没有 `workspace_read` 权限时隐藏
  Files 视图）只为了界面清爽，真正的权限拦截全部在服务端完成。

**常见错误：** 调试完忘了删 `console.log(response)`；新加的持久化 Pinia store 把
token 存进了本地；为了“保留格式”直接拿 `v-html` 渲染工具返回结果。

**边界：** 隐藏当前无权操作的功能能减少干扰（U10），但不能代替后端鉴权。如果前端拿不准
权限标志，宁可照常显示按钮，点下去由服务端判断。

**自查方法：** 走完操作流程后，打开 DevTools → Local Storage（检查 `memoh:query-cache`
和所有新增 key）以及控制台，搜一遍有没有敏感字段。

**保证方式：** 结构（查询缓存自动剥离敏感字段与整条排除）；文字（其余部分，来源：用户确认；无法完全写成静态代码检查，因无法单靠 AST 语法判断任意接口新字段是否含业务敏感凭据）。

### U2. 用户输入不丢失

**适用场景：** 用户输入、选择、上传或修改配置：表单、输入框、下拉选择器、开关，尤其是
同一屏幕还在展示会自动刷新的服务端数据时。

**规则：** 用户填了一半的内容、主动选中的筛选项和草稿，在后台刷新、组件重绘、切窗口或
切 tab 后都必须原样保留；后台数据刷新绝不能冲掉用户改过的值；用户明确选过的配置优先于
系统默认值。

**原因：** 填好的表单突然被清空是最伤信任的事，而且用户往往要等点下保存、发现存进去的是
旧值时才反应过来。Pinia Colada 默认会在切回窗口时重新拉取活跃查询，每次返回新对象；
如果页面只要看查询数据变了就往表单里覆盖，用户切个窗口回来，刚改了一半的内容就没了。

**本仓库的实现：**
- 拿服务端数据做初始值的表单，统一用 `useServerSyncedRecord` / `useServerSyncedScalar`
  （`composables/use-server-synced-form.ts`）。切到另一个对象（比如换了一个 bot 或
  provider）时重置表单；同一个对象后台刷新时，只更新用户还没动过的字段。
- 保持 `refetchOnWindowFocus` 开启：只读视图靠它保持数据最新（helper 文件头写了原因），
  防覆盖由上面的表单 helper 兜底。
- 聊天输入框按 bot 记住用户选过的模型和推理强度（`pages/home/components/chat-pane-send.ts`），
  不会在刷新后退回 bot 默认值。
- 多步操作刷新页面后能接着往下走，不会重复创建：创建 bot 时会把刚建好的 bot id 存下来，
  刷新后继续配置同一个 bot。

**常见错误：** 写 `watch(() => query.data.value, d => Object.assign(form, d))` 把后台
刷新直接盖进表单；在 `onMounted` 里把选择器重置回默认值；消息还没发送成功就先把输入框
清空了。

**边界：** 用户主动切换到另一个对象时，重置表单是正常行为。密码和密钥输入框的草稿绝不
落盘保存（U1）。

**自查方法：** 改一个表单字段但别保存，切去别的软件窗口再切回来，确认刚才改的字还在；
再切到另一个 bot 后切回来，确认两边各自显示自己已保存的值。

**保证方式：** 结构（服务端初始化的表单走上述 helper）；文字（其余部分，来源：用户确认；多步向导与局部草稿的边界依赖业务流语义，无法统一写成单条静态 lint）。

### U3. 界面显示的状态属实

**适用场景：** 显示状态、进度、成功、报错、数量、“实时”标识，或可能已过期的数据。

**规则：** 界面只显示已经确认的真实状态：“加载中”代表真有请求在跑，“已保存”代表服务端
已经确认落库，“实时”代表画面内容真的在源源不断到达。报错显示在用户当前视线所在的位置，
用用户的语言说清楚，并给下一步出路。普通 toast（包括日常报错、成功和信息提示）默认 4 秒
自动消失，鼠标移上去或聚焦时暂停倒计时；**带操作按钮（action）的 toast** 走独立长驻路径
（至少停留 8 秒，或传 `duration: Infinity` 留到用户点按钮或手动关闭为止）。

**原因：** 用户是看着界面状态做下一步动作的——没存上却报“已保存”，或者黑着屏却显示“已连接”，
比完全不显示状态更耽误事。日常报错大多是当前页面的即时反馈（比如复制失败、保存失败），按
Sonner 和 Ant Design 的习惯 4 秒自动收起，省得连续报错时在右上角攒一排红框；但只要 toast
上带着操作按钮（比如“撤销”或“查看后台任务详情”），4 秒闪过就会让用户还没反应过来要不要点，
按钮就已经没了（Material Design 3 与 IBM Carbon 要求带操作的通知延长停留或常驻，负责人于
2026-10-28 确认）。

**本仓库的实现：**
- 报错文案一律走 `resolveApiErrorMessage(error, fallback)`：按稳定错误码查找当前语言的
  `errors.<code>`（带 `args` 插值）；无对应条目时按 HTTP 状态码兜底（4xx 含 429 走 `errors.http.*`，
  5xx 走 `errors.internal`，499 静默忽略），再按流错误事件兜底（`errors.internal`，`fault === 'canceled'`
  静默忽略），最后回退到调用方传入的 `fallback`。**它绝不向用户显示服务端返回的原始 `message`/`detail`**
  （仅显式构造的 `UserFacingError` 例外）。业务分支判断一律用 `isApiErrorCode(error, 'x.y')`，绝不拿报错
  字符串做匹配（详见 `.agents/skills/memoh-error-handling/SKILL.md`）。流式错误统一通过 `error` 事件追加到消息块（旧 `processing_failed` 已移除）。
- 弹窗里的提交操作统一走 `useDialogMutation`：失败时自动弹错误 toast 并返回 `false`，
  弹窗保持打开，不弄丢用户刚填的内容。
- 自动保存成功时不弹提示，失败时才弹报错并回滚界面上的乐观更新（ui-patterns skill `references/saving-and-notifications.md`）。
- toast 由 `@felinic/ui` 的 `toast`（`packages/ui/src/components/sonner/toast.ts`）
  统一提供，由 `DEFAULT_DURATION = 4000` 控制默认 4 秒消失，鼠标悬停或聚焦时暂停；应用操作
  与依赖操作 store 为带按钮的 toast 设了 8 秒（`ACTIONABLE_TOAST_MS = 8000`），传
  `duration: Infinity` 则常驻到手动关闭。缺口：`toast.ts` 的 `create()` 目前还没在检测到
  `options.action` 时自动切换长驻时长，调用方需显式传 `duration`。
- 实时画面状态以真收到画面帧为准，不能看底层连接标志：WebRTC 在第一帧画面出来前就会报
  `connected`（ui-patterns skill `references/degraded-and-destructive.md`）。
- 结果未知就如实显示未知：流断开的依赖操作在服务端对账出结果前，不展示重试按钮
  （`references/architecture.md` § 工作区依赖操作契约）。

**常见错误：** 接口还没返回就先弹 `toast.success`；为了“界面干净”在 `catch` 里把报错吞了；
直接拿 socket 的连接标志点亮绿点；给带操作按钮的 toast 用默认 4 秒时长，用户来不及点就没了。

**边界：** 后台刷新期间可以先展示缓存里的旧数据（U4）；但如果用户接下来的操作依赖最新状态，
要标明“正在刷新”或等刷新完再让点。

**自查方法：** 手动制造各种失败（停掉后端、让接口回 4xx/5xx、操作到一半断网），确认每条失败
路径最后都有人话报错和下一步操作，且没有任何地方误报成功。

**保证方式：** 结构（报错 helper、`useDialogMutation`）；文字（其余部分，含带按钮 toast 的
时长，来源：用户确认；状态与真实后端/视频流帧是否一致属于运行时语义，无法仅靠静态 AST 判定）。目标：结构（`toast.ts` 在有 `action` 时自动切长驻时长）。

### U4. 已获取的数据立即显示；加载反馈遵守固定时限

**适用场景：** 渲染服务端数据（列表、详情页、下拉选择器、侧栏分区），或在等待请求与操作结果
时显示加载反馈。

**规则：** 之前拉取过的数据在打开页面的第一帧直接渲染，同时在后台静默刷新；用户重新点开看过的
页面时，绝不能退回空白页或重新转圈。当还没有任何缓存数据、或者正在等某个操作跑完时，按等待
时长分档反馈：

- **100 ms 内**：用户点下后 100 ms 内界面必须有肉眼可见的响应（按钮按下态、忙碌态或直接出结果）。
- **200 ms 内完成**：直接出结果，不显示任何加载提示（不闪转圈 spinner、骨架屏 skeleton 或进度条）。
- **超过 200 ms 仍未完成**：显示加载提示；一旦显示出来，至少停留 200 ms 再消失。知道内容排布形状
  时用同尺寸的骨架屏；点按钮触发的操作直接在按钮里转圈。
- **可能超过 10 s**：显示当前走到哪一步或进度百分比，且不阻塞用户去干别的事；如果非锁死界面不可，
  必须提供“取消”按钮。

**原因：** 以前有个列表每次点开都重新发请求，每次让人干等半秒；用户一天要来回切几十次页面，这种
等待会不断叠加。反馈怎么给取决于等多久：100 ms 内的变化人眼觉得是立刻响应；200 ms 内就能回来的
请求如果闪一下转圈或骨架屏，反而晃眼；转圈刚出来不到一眨眼就消失同样是闪烁；一旦超过 10 s，人的
注意力就会离开当前任务，必须告诉他进展到哪了。这套数值来自 Nielsen 响应时间界限（0.1 s、10 s）、
Google RAIL 模型（100 ms 内响应）、Material Design 3 加载规范（200 ms 内直接出内容）和 spin-delay
的默认最短停留时长（200 ms），负责人于 2026-10-27 确认采用。

**本仓库的实现：**
- 统一用 Pinia Colada 的 `useQuery` 搭配 SDK 生成的查询配置或 key 拉数据。这是全站唯一的服务端
  缓存；自己写在 `onMounted` 里塞进本地 `ref` 的数据没有任何缓存。
- 默认缓存策略（Colada 0.21，`main.ts` 未做全局覆盖）：5 秒内算新鲜；最后一个用它的组件卸载后
  缓存留 5 分钟；过期后在组件挂载和窗口重新聚焦时后台重拉。成功的查询还会自动落盘到 localStorage，
  连强刷页面都能第一帧直出。
- 骨架屏一律绑 `isPending`（代表手里还没有任何数据）。注意 `isLoading` 在每次后台静默刷新时也是
  `true`，拿它绑骨架屏会导致每次重进页面都重新闪一遍加载态；它只能用来做角落里的轻量刷新提示。
- 加载形态从四档里选（`packages/ui/skills/ui-owners/SKILL.md` § 加载与空占位原语），只准用现成的加载 owner 组件：
  检查脚本会拦截 `apps/web` 里手写的裸 `animate-spin`。空状态和加载态都要保留外层页面框架
  （ui-patterns skill `references/loading-and-empty-states.md`）。
- **时限现状与存量豁免**：`LoadingButton`（`components/loading-button`，`loadingDelay` 默认
  200 ms）和文件树展开（`treeSpinnerDelayMs`）已经做了 200 ms 延迟显示；新写的按钮异步请求一律用
  `LoadingButton`。老代码里直接传 `Button` 的 `:loading` 属性（78 处）和现有骨架屏组件属于历史
  遗留，进入加载态会立即显示且没有 200 ms 最短停留，**不在业务层逐个改写**；以后如果要统一加上延迟
  与最短停留，直接在 `@felinic/ui` 底层组件里改一处即可。
- **对话输入框首帧直出（Composer-First Entry）**：所有进入对话的入口（冷启动、刷新、新建对话、切换历史会话、切换 Bot、深链）都在**第一帧渲染输入框并允许立即打字**，路由守卫对已确认过引导的老账号直接放行、后台校验，绝不用网络或 store 加载状态（用户信息、Bot 列表、会话列表、历史消息、模型目录、WebSocket）隐藏或 `disabled` 输入框；加载期间只暂缓发送（`handleSend`），位置从首帧起确定（详见 `references/architecture.md` § 路由与三层常驻布局）。
- 聊天记录有单独的缓存契约：切走再切回的会话，只有在 SSE 失效通知的覆盖期内才直接渲染本地缓存
  （见 `references/architecture.md` § 流式传输）。

**常见错误：** 为了“保险”在 `useQuery` 旁边自己又建一个 `loading` ref 或重复发请求；为了少闪加载态
去把某个查询的 `staleTime` 改大；查询 key 里塞了每次打开都会变的值；用 `loadingMessages` 或 `loadingChats`
把对话输入框设为 `disabled` 或 `invisible`；请求刚发出 0 ms 就闪出转圈；
转圈刚露头就秒退；超过 10 s 的慢操作只放一个死转圈还把全屏锁死。

**边界：** 不能拿过期状态做决定的敏感数据（比如访问控制权限）不落盘持久化，等拉回来再显示或标明
正在刷新。首次冷加载同样按上面的 200 ms 时限展示骨架屏。对话入口仅在“全新浏览器首次登录未知账号”或“URL 指向本标签页未记住的另一个 Bot”这两种完全不知道目标 Bot 是谁的情况下，允许等待一次查询返回后再显示输入框。

**自查方法：** 打开页面 → 切走 → 再切回来：第一帧必须直接有内容。打开 DevTools 网络限速（Slow 4G）模拟快慢请求：
老账号冷启动或切未缓存会话时，输入框在第一帧即可打字；200 ms 内返回的不闪加载态；慢请求在 200 ms 后才出加载态，且至少稳住 200 ms。

**保证方式：** 结构（`LoadingButton` 默认 200 ms 延迟、回访账号路由守卫本地放行）；机械检查（脚本拦截手写 `animate-spin`）；文字（其余部分，来源：用户确认；不同接口的时延与骨架同形度需在运行态实测，静态代码无法直接断言网络耗时）。

### U5. 过渡中的每一帧都是有效画面

**适用场景：** 元素出现、消失、移动或替换：路由切换、列表与详情互切、弹窗和面板开关、加载态变成
正文、组件挂载与卸载。

**规则：** 切换过程中的每一帧，截下屏来都必须是一张排版正常的画面：不闪白屏、不同时叠着新旧两套
内容、不因为上面某个元素早卸或晚卸一拍而把下面的内容撞得上下乱跳。

**原因：** 只要中间有一帧坏掉——比如旧面板先塌了新面板还没挂上，或者滚动条突然出现把页面往左挤了
十几像素——用户眼睛看到的就是“页面卡了一下、闪了一下”，哪怕最后停住的画面是对的，产品也会显得很糙。

**本仓库的实现：**
- 聊天主区（`MainSection`）常驻挂载在 `App.vue` 里，在聊天和 `/settings` 之间切换路由时绝不卸载；
  因为 `KeepAlive` 保不住 dockview 的分屏布局，一旦卸载重挂就会闪屏（见 `references/architecture.md`
  § 布局系统）。绝不要把 `MainSection` 挪进 `<RouterView>`。
- 离开设置页时，等离场动画播完再真正切走路由：`pages/settings-section/index.vue` 会捏住路由守卫的
  `next()`，直到 `after-leave` 触发才放行。卸载动作一律排在动画结束之后。
- 页面内的“列表 ↔ 详情”切换，用 `useRoutedViewSwap`（`composables/useViewSwap.ts`）配 `@felinic/ui`
  的 `SwapTransition`：左右两屏同步交叉推拉，不会出现“旧的先滑走留白、新的再滑进来”的两段跳动。
- 同级页面共用的滚动容器加上 `[scrollbar-gutter:stable]` 预留滚动条槽位，长短页面互切时不会左右横跳。
- 容器宽度固定、超长文字截断，不让布局宽度跟着文字长短乱晃。弹窗高度变化用 `AutoHeight` 和
  `DialogPanel` 的属性控制，不手写 `max-height`。
- 动效规范与 Tailwind v4 的过渡坑见 `packages/ui/AGENTS.md` § 交互反馈、按压缩放与动效档位。

**常见错误：** 父子组件各写各的 `v-if`，切换不在同一拍；同一个位置拿 `<Transition>` 换两个元素却
忘了加 `mode`，导致新旧两个元素短暂同屏把高度撑爆；出了闪烁不去修生命周期，反而套个 `nextTick` 或
`setTimeout` 遮丑。

**边界：** 干脆利落地直接切换（完全不加动画）也是合格画面。这条规则管的是“别出现坏掉的中间帧”，
拿不准动画怎么写时，直接切（ui-patterns skill `references/layout-and-navigation.md`）。

**自查方法：** 打开 DevTools 的 Animations 面板把速度调慢到 10%（或用 Performance 录屏勾选 Screenshots），
一帧一帧拖着看。

**保证方式：** 文字（来源：用户确认；过渡中间帧的视觉排版完整性依赖浏览器真实渲染管线与帧时序，静态 AST 无法判断两块 DOM 动画是否撞车）。

### U6. 每个状态都提供后续操作；确认强度与后果相称

**适用场景：** 空状态、报错、失败、被拦截或只成功了一半的状态；以及会删除数据、覆盖配置、花钱或
不可撤回的操作。

**规则：** 任何非正常状态都要说清楚发生了什么，并给用户留好下一步出口（重试、去别处配置、或先跳过
稍后再说）。弹确认框的力度要跟后果轻重匹配：能随时改回来的操作直接执行，别弹窗烦人；真会删掉数据
或无法撤销的操作才确认一次，并在确认框里写明具体会丢掉什么。

**原因：** 报错后只给个死胡同式的“重试”，或者刷新一下就把副作用再执行一遍，会把用户彻底卡死；反过来，
如果连关个普通开关都弹窗问“你确定吗”，用户很快就会看都不看一路点确定，等到真删库那天也就顺手点下去了。

**本仓库的实现：**
- 创建 Bot 的进度页是标准样板：工作区容器创建失败时，页面会针对同一个已建好的 Bot 提供“重试工作区”和
  “稍后处理”（继续完成引导或直接进 Bot 详情页）两条路；重名冲突时直接给链接跳去已有的同名 Bot；中途刷新
  页面也能接着同一个 Bot 往下走（`pages/bots/new-progress.vue`，store `bot-create-progress`）。
- 删除确认统一用 `ConfirmDeleteDialog` 组件（`packages/ui/skills/ui-owners/SKILL.md` § 弹窗与确认原语）。

**常见错误：** 失败时只飘一个 4 秒就消失的 toast，页面上什么状态都不留；给一个随时能拨回来的开关加确认
弹窗；确认框只冷冰冰写一句“确定删除吗？”，不写删的是哪个对象、会连带清掉什么。

**边界：** 网络抖动这类临时失败可以在后台静默重试（流连接统一走 `useRetryingStream` 指数退避重连），但
有业务副作用的操作重试前必须保证幂等，或者让用户手动点重试。

**自查方法：** 挨个触发空状态、接口报错、断网、无权限、重名冲突，确认每种状态下用户不用按浏览器刷新键
也能继续操作或体面退出。

**保证方式：** 文字（来源：用户确认；某个状态应该提供“重试”“去配置”还是“跳过”以及操作是否可逆，取决于具体业务后果，无法用通用正则静态判定）。

### U7. 用户控制

**适用场景：** 用户没点鼠标时后台自己发生的事（后台事件、agent 跑任务、定时器、自动保存），或改动涉及
焦点、面板、tab、滚动条位置、浏览器历史记录、键盘快捷键。

**规则：** 只有用户自己的操作才能挪动焦点：后台任务可以静默更新已经打开的内容，但绝不能擅自切走用户正在
看的面板、tab 或页面。点刷新和浏览器后退键要能回到刚才的位置。浏览器自带的操作（前进后退、Cmd/Ctrl+点击
在新标签页打开、选中文字复制、Cmd+F 页内搜索、页面缩放）必须照常好用。

**原因：** Memoh 的 agent 一直在后台跑任务、调工具。以前 agent 一调浏览器或桌面工具，前端就自动帮用户切
tab、弹面板，用户正在看文档或写字时屏幕突然被抢走，非常恼火。

**本仓库的实现：**
- 工作区面板（`store/workspace-tabs.ts`）：后台事件只允许更新 tab 里指向的数据（比如会话内容、标题）或
  清理已关闭的 tab；只有用户自己点击触发的路径，才允许调 `focusPanel`、`activateChatSession` 或带激活
  参数的 `open*` 函数。需要“跟随 agent 视角”时，做成显式按钮让用户自己点。
- 用户刷新后还想留在原地的页内状态（当前选中的 tab、过滤条件、处于列表还是详情）写进 URL 查询参数：用
  `useSyncedQueryParam`（内部走 `router.replace`，不会污染后退历史栈）和 `useRoutedViewSwap`。
- 页面左上角的返回按钮用 `useBackOr(fallback)`。
- 页面跳转入口用真正的链接（`RouterLink` 或 `<a href>`），保证用户可以右键或按住 Cmd/Ctrl 在新标签页打开。
- 焦点顺着用户的操作往下走：当前这一步填完确认后，光标自动落进下一步要填的输入框（ui-patterns skill `references/forms.md`）。

**常见错误：** 后台一有新会话进来就把主视图切过去；切页内 tab 时用了 `router.push` 导致用户按十次后退键
还在同一个页面里打转；拿 `<div @click>` 冒充链接导致没法在新标签页打开；绑快捷键时把浏览器自带的复制、
搜索或刷新给劫持了。

**边界：** 响应用户刚刚那一下点击时可以动焦点（比如用户亲手点了“在 Desktop 中打开”，或者提交完上一步把光标
移进下一步输入框）。安静无打扰且随时能改回来的自动保存不在此限。

**自查方法：** 让 agent 在后台不停调工具，同时你切到另一个 tab 看文件，确认面板和焦点纹丝不动；点进深层页
（比如某个 Bot 详情的某个子 tab 加筛选词）按刷新，确认还停在原处；按住 Cmd/Ctrl 点导航菜单，确认能在新标签页打开。

**保证方式：** 文字（来源：用户确认；同一个 `focusPanel` / `router.push` 调用在用户点击回调里合法、在后台 SSE 事件回调里违规，静态规则难以跨调用栈完整追踪触发源）。

### U8. 在所有运行环境下成立

**适用场景：** 所有改动；尤其是新增文案、颜色、可点击元素、布局、新页面、长连接视图，或跨 tab 共享的状态。

**规则：** 任何改动在下面这些真实环境里都必须正常工作：手机窄屏与桌面宽屏、浅色与深色模式、中英日三语、
用户调大系统字号、弱网或断网重连、连开好几天不关的标签页、同一账号开多个标签页、纯键盘操作，以及读屏软件。
无障碍与对比度标准如下：

- **文字对比度**：正文和次要文字与背景的对比度至少 **4.5:1**；大号文字（`≥ 24 CSS px`，或 `≥ 18.66 CSS px`
  粗体）至少 **3:1**。输入框占位文字（placeholder）需要清晰可读且明显浅于正文（深色模式下实测为 `5.7–6.5:1`，
  超过 4.5:1）。
- **控件与焦点对比度**：控件获得焦点时的边线或焦点环、选中态和必要图标，与相邻颜色的对比度至少 **3:1**（禁用态
  除外）；未聚焦时的静态细边框按现代组件库（Radix Colors Step 6–7、shadcn/ui）的弱边线惯例设计（深色模式实色灰
  为 `1.54–1.76:1`），不硬卡 3:1，但深浅色下轮廓都要看得清。
- **点击热区**：可点击目标至少 **24×24 CSS px**；如果做成更小的图标，以它中心画一个直径 24 px 的圆，不能碰着
  旁边其他可点击目标的圆（正文句子里的文字链接除外）。
- **键盘与焦点**：所有功能纯靠键盘都能走通；焦点框时刻清晰可见；焦点进了任何区域都能靠键盘走出来，不出现键盘陷阱。
- **缩放与窄屏重排**：文字放大到 200% 时内容和功能不缺失；视口缩到 320 CSS px 宽时，除了数据表格这类必须双向
  滚动的内容外，不出现横向滚动条。
- **读屏与减动效**：状态消息（保存结果、报错、进度变化）不挪焦点也能让读屏软件播报出来；遵守系统“减少动态效果”
  （`prefers-reduced-motion`）设置。

**原因：** 这些全是我们用户的真实日常：桌面端一挂就是好几天，手机用户直接用移动壳，中文和日文翻译出来经常比英文
短一截或长一倍。只在你自己的宽屏显示器、英文、浅色模式下能看的页面，只算写了一半。上述数值来自 WCAG 2.2 的
1.4.3、1.4.11、2.5.8、2.1.1、2.1.2、2.4.7、1.4.4、1.4.10、4.1.3（A/AA 级）及 2.3.3（减动效），并结合现代组件库
的弱边线实践，由负责人于 2026-10-28 确认。

**本仓库的实现：**
- **三语国际化**：支持 `en`、`zh`、`ja`（`i18n/locales/`），新增文案必须三个语言文件同时补齐，绝不硬编码文字。
- **深色模式**：靠全站只用语义颜色 token、不写死色值来自动适配（`packages/ui/AGENTS.md` § 颜色与零色度交互叠色梯）。
- **字号缩放**：凡是跟文字相关的尺寸一律用 `rem`，根字号跟着用户在设置里调的档位走（检查脚本会拦违规的 `px`）。
- **响应式断点**：窗口小于 `768px` 时聊天区切换挂载移动端外壳（`useIsMobile` 是全站唯一的 JS 断点），其余局部
  排版一律用 Tailwind 的 `md:`；桌面端窗口最小宽度为 `960px`；窄面板自动折行重排，绝不横向撑破。
- **长连接与后台节流恢复**：流连接统一走 `useRetryingStream` 自动重连；会话列表和消息缓存靠服务端推的失效事件
  同步。因为浏览器和 Electron（默认开启 `backgroundThrottling`）会对切到后台超过 5 分钟的标签页严厉节流定时器
  （Chrome 最多每分钟才跑一次链式定时器），所以标签页重新切回前台（`visibilitychange`）时，必须直接向服务端对账
  同步状态，绝不能指望后台定时器准点跑完。
- **键盘与无障碍播报**：所有交互控件直接用 `@felinic/ui` 的真按钮和链接；toast 容器自带 `role="status"` 与
  `aria-live="polite"`；`@felinic/ui` 已内置 `prefers-reduced-motion` 处理，业务里自己写的动画用
  `motion-reduce:` 或 `motion-safe:`。
- **对比度实测与下次调色基线（由本 skill 自带的 `scripts/check-contrast.mjs` 计算）**：
  - **深色模式全部达标**：正文 `15.0:1`，次要文字 `6.6–7.6:1`，占位文字 `5.7–6.5:1`，输入框聚焦边线
    `4.5–5.1:1`，静止实色灰细边 `1.54–1.76:1`（比 shadcn 默认的 `1.47:1` 更清晰）。
  - **浅色模式已达标项**：正文 `16.8:1`，次要文字 `5.0–5.5:1`，输入框聚焦边线 `11.3–11.7:1`。
  - **浅色模式待调色项（留待下次组件库重构颜色时跑 `node scripts/check-contrast.mjs` 统一修）**：浅色占位文字
    `--field-placeholder`（`oklch(0.66 0.004 95)`）只有 `2.94–3.11:1`（把亮度 `L` 降到 `≤ 0.56` 即可达到
    `4.5:1`）；浅色透明底表单框的静止细边 `--field-edge-rest`（`11%` 黑）只有 `1.28:1`，在亮屏下容易融进背景；
    按钮键盘焦点环 `ring-ring/30` 因叠了 30% 透明度，浅色为 `1.4:1`、深色为 `2.0–2.2:1`。

**常见错误：** 写完只在英文、浅色、大宽屏下看一眼就交差；给按钮或侧栏写死像素宽度导致中文或日文被截断；手写
`text-[13px]`；把会话状态存在模块全局变量里导致另一个 tab 没法同步失效；小于 24 px 的小图标按钮挨个挤成一排；
状态变了只改个颜色，读屏软件完全不知道。

**边界：** 手机横屏（宽度 `≥ 768px`）按设计直接使用桌面外壳。

**自查方法：** 在改动的页面上挨个切一遍：深色模式、中文和日文、把面板拖到最窄、浏览器放大到 200%、开网络限速、
给同一个 Bot 再开第二个标签页，最后不用鼠标光按 Tab 键把所有控件走一遍。新增或修改颜色 token 时运行
`node scripts/check-contrast.mjs` 验算对比度。

**保证方式：** 机械检查（脚本检查 `px` 缩放与 `packages/ui` 内的颜色，并附带 `scripts/check-contrast.mjs` 验算 OKLCH 对比度）；文字（其余部分，来源：用户确认；多语言折行、320px 窄屏溢出与跨 Tab 同步需在运行态多环境验证）。

### U9. 同一概念在各处一致

**适用场景：** 要做的东西在产品别的地方已经有了（一行列表、一个按钮、一种状态标签、一个菜单、一个空状态、一套
保存交互），或者跟现有的某个东西很像。

**规则：** 同一个概念在全站只有一种长相和一种交互方式，长相直接反映它的职责：干同一件事的控件必须长一样，干不同
事的控件必须长得有区分。

**原因：** 用户只需要学一次怎么用这个产品。如果同一个操作在 A 页面是个图标、到 B 页面变成了文字块，或者明明是两个
完全不同的功能却长得一模一样，用户每次都得重新猜。

**本仓库的实现：**
- 职责不同，长相就不同：切换视图的 `Tabs` 与切换参数值的 `SegmentedControl`、行内可点文字 `TextButton` 与标准按钮、
  只做解释的 `InfoHint` 与能点进去干活的 `ActionCard`（详见 `packages/ui/skills/ui-owners/SKILL.md` § 易混基础原子选型）。
- 凡是 `ui-owners` 字典里已经收录的结构，直接拿现成 owner 拼（`packages/ui/skills/ui-owners/SKILL.md` § 选型速查表）。放着现成的行、表单块、
  卡片或数值块不用，自己在页面里拿 `div` 手搓一套，是本仓库复发率最高的问题。
- 保存按钮放在哪按页面类型定（自动保存 vs 底部操作栏，见 ui-patterns skill `references/saving-and-notifications.md`）；排在同一行的输入框和按钮高度必须对齐。

**常见错误：** 去别的页面挑一段看着顺眼的 HTML 复制过来改改；给某个组件硬塞一个 prop 让它去干另一个组件的活；
觉得“就这一页特殊”，在页面里直接绑 class 改掉共享组件的样式。

**边界：** 不同组件可以有自己独特的细节（比如带阴影的滑块、特定圆角），只要走 token 定义即可。只有当两个地方的业务
关系确实不同时才保留差异；如果只是因为“我觉得这一页这么微调更好看”，一律向现有 owner 统一。

**自查方法：** 在产品里再找出两处展示同一个概念的地方，跟你的实现并排放在一起对比。

**保证方式：** 结构（`@felinic/ui` 与业务 owner）；机械检查（脚本拦截页面向组件注入样式及卡片外手抄 `min-h-[3.75rem]`）；文字（其余部分，来源：用户确认；“同形异码”用裸 `div` 换一套类名拼出相同概念，语法合法且类名多变，无法靠简单正则穷尽）。

### U10. 克制：每屏一个重点，高级功能按需显示

**适用场景：** 往界面上增加任何看得见的东西：新区块、徽标（badge）、提示语、说明文字、按钮、设置项、强调色、动画。

**规则：** 每一屏只突出一个核心用途，其余次要信息要么压低视觉权重，要么收进有明确名字的二级入口里。首屏只摆用户
眼下立刻要看、要用的内容；低频和高级配置等用户主动点开再展示。文案只写读者此时此刻做决定需要的那句话。

**原因：** 界面上每多放一个元素，所有用户每次打开这页都要分一点注意力去扫它，而它往往只对极少数人有用。单个看都
觉得“加上挺好”的东西，堆满一屏就成了噪音。

**本仓库的实现：**
- 点进功能页的第一屏只回答“现在运行正不正常”；复杂的配置动作收进带名字的入口（比如 `ActionCard`），点开后用单一
  任务弹窗完成（ui-patterns skill `references/progressive-disclosure.md`）。
- 一切正常时安静待着，不挂“运行正常”横幅；只有出了需要用户处理的异常时才亮提示（ui-patterns skill `references/degraded-and-destructive.md`）。
- 全站 90% 的面积保持黑白灰中性色，品牌紫色只在真正需要点睛的地方克制使用（`packages/ui/AGENTS.md` § 颜色与零色度交互叠色梯）。
- 文案一行干一件事：控件旁边已经写清楚的信息，绝不在副标题或 tooltip 里换个词再复读一遍。

**常见错误：** 每个表单项下面都挂一行灰字说明；给默认状态也贴个 badge；静默自动保存每次成功都弹 toast；把只读的
诊断信息和真会改配置的危险按钮混塞在同一个“高级设置”折叠块里。

**边界：** 帮用户摸清现状的概览或确认界面，应该把当前生效的默认值大大方方亮出来让人安心。精简首屏是把低频功能挪到
合适的二级位置，不是把功能删掉。

**自查方法：** 先用一句话说出当前这一屏的核心用途，然后挨个遮住页面上的元素问自己“拿掉它用户还能不能顺利干完这件事”——
拿掉也毫无影响的，直接删掉。

**保证方式：** 文字（来源：用户确认；一屏的核心焦点是什么、哪行说明文字属于冗余复读，属于信息层级与读者判断，无法写成布尔语法规则）。

## 2. 面向维护者的承诺

### M1. 优先使用平台，其次使用库，不自行实现

**适用场景：** 需要某项通用能力：弹出浮层（popover）、焦点锁定、拖拽、虚拟滚动列表、防抖、
媒体查询、剪贴板读写、日期格式化、动画过渡。

**规则：** 浏览器和框架原生就有的能力（HTML、CSS、浏览器 API、Vue），直接用原生的；原生没有的，
用仓库里已经装好的库；连现成库也没有时，按下面的标准评估后再引入维护良好的新依赖。凡是平台或
现有库已经解决的事，绝不自己手写。

**原因：** 自己手搓的实现几乎一定会漏掉原生和成熟库早就踩平的边角情况（键盘导航、焦点管理、中文
输入法组合键、无障碍属性、动画中断时序），还会白白多出一份以后要人维护的代码。

**本仓库的实现：**
- 已锁定的标准库：基础无头交互一律通过 `@felinic/ui` 间接使用 Reka UI（业务层绝不直接 import Reka UI）、
  VueUse、vee-validate + Zod、Pinia Colada、markstream-vue（配 Shiki / Mermaid / KaTeX）、
  `lucide-vue-next` 与 `@memohai/icon`，以及统一处理日期和相对时间的 `utils/date-time.ts`。
- 新引入依赖的规矩：必须在 PR 里说清楚为什么原生和现有库干不了、新包的体积与维护健康度、全站还有
  哪些地方能复用它，并提前向团队报备。桌面端内置 Chromium 版本以 `apps/desktop/package.json` 中的
  Electron 版本为准，老内核不支持的新 CSS 特性用库兜底。

**常见错误：** 自己拿 `div` 拼下拉菜单；自己手写 `setTimeout` 防抖函数；底层组件本来就支持点外面
自动关闭，自己又在 `window` 上绑一层点击监听；拿 `setTimeout` 去赌 DOM 什么时候渲染完。

**边界：** 可以把第三方库包成项目自己的共享组件（owner），只要里面还是调那个库就行。三五行的纯函数
小工具不在此限，可以按需写并说清理由。

**自查方法：** 准备写工具函数前，先搜一遍 `@felinic/ui`、VueUse 和现有的 `composables/`。

**保证方式：** 机械检查（ESLint 禁止 `apps/web` 直接 import `reka-ui` 或 `@fortawesome/*`）；文字（其余部分，来源：用户确认；是否重复造了防抖或浮层逻辑属于算法意图识别，无法仅靠 import 名静态穷尽）。

### M2. 一个概念一个 owner

**适用场景：** 写组件、composable、store 或样式，或者顺手改进现有的实现。

**规则：** 凡是已经有共享组件（owner）的概念，一律直接拿 owner 组合；要优化外观或交互，直接去改
那个 owner 本身，让全站所有用到的地方一起变好。做全新的东西时，第一次出现先写在当前页面自己的目录
里；等到第二个页面也要用同一个概念时，再把它抽进共享层变成正式 owner。抽进共享层时，只暴露当前真
正在用的属性，接口越窄越好，给自己留好以后调整的后路。

**原因：** 同一个概念只要在代码里存了两份，早晚会越长越歪：同一种列表行最后冒出三种内边距、同一种
状态冒出两种色号，修完东边漏西边。反过来，如果某个结构只在单页用了一次就急着抽成“大而全的通用组件”，
接口全靠凭空猜，等真遇到第二个场景时发现根本套不上，只能不停往上摞布尔开关和特判，最后把共享组件写成
没人敢动的屎山（M8）。

**本仓库的实现：**
- 三层归属结构：`@felinic/ui`（跟业务无关的基础原子组件，位于 `packages/ui` 子模块）→ `components/`
  下的业务共享 owner（完整字典见 `ui-owners` skill）→ `pages/` 下的具体页面。
- 晋升路径：只在单个页面里用的子组件放 `pages/<feature>/components/`；当第二个页面也需要同一种结构时，
  再提拔到 `components/` 成为业务 owner。只有完全不含业务语义的基础控件才进 `@felinic/ui`——因为一旦发进
  基础库，所有消费端都会依赖它，加进去容易、删掉极难。
- 改共享层（`@felinic/ui` 或业务 owner）前要先经过负责人点头。改 `@felinic/ui` 需要在 `felinics/ui`
  独立仓提 PR，合并后再回主仓更新 submodule 指针。
- 如果你在调某一个页面时调出了更舒服的间距、状态或动画，只要它对全站同类地方都有益，就直接沉进共享 owner；
  如果只适合这一页自嗨，就别上线。
- 新增业务 owner 后，同步登记到 `ui-owners` 字典，并在开发组件墙（`/dev/components`）上补一个活体示例。

**常见错误：** 怕改坏公共组件，干脆把公共组件复制一份到自己页面里改；在调用处绑一堆 `class` 把公共组件
原本的间距或背景色硬顶掉；为同一份后端数据再开一个 Pinia store；某个结构总共就用了一次，却提前在公共目录
里造了个带七八个预留插槽的“万能组件”。

**边界：** 空间排布关系确实跟标准组件完全不是一回事时，允许留在页面里手写（见 `packages/ui/skills/ui-owners/SKILL.md` § 何时保留手写）。长得有点像但业务含义完全不同的两个东西，算不同概念，各留各的。只用一次的页面专属块就安心放在
页面目录里，别为了“万一以后要用”提前抽公共组件——但哪怕留在页面里，照样要用 `@felinic/ui` 的原子组件和 token
来搭（M1、M4）。

**自查方法：** 动手写之前，先按功能去 `@felinic/ui`、`components/` 和参考页面里搜一圈（注意代码里的名字未必
叫你嘴里说的那个词），数数它在全站出现了几次：第一次就地写，第二次抽共享。

**保证方式：** 结构（现有 owner 体系）；机械检查（脚本拦截页面向组件注入违规 class）；文字（其余部分，来源：用户确认；何时属于“第二次出现该抽共享组件”需要结合跨页面职责判断，无法用静态行数或引用数硬切）。

### M3. 服务端数据只有一条访问路径

**适用场景：** 拉取或修改服务端数据、定义查询 key、展示加载或报错状态，或者在两个地方用到同一份服务端数据。

**规则：** 所有接口调用一律走自动生成的 `@memohai/sdk`。服务端数据一律放进 Pinia Colada 的查询（`useQuery`）
和变更（`useMutation`）里，靠使查询缓存失效（`invalidateQueries`）来更新数据；缓存副本、加载态和重试全部交由
查询层统一打理。查询 key 必须把所有会影响返回结果的参数都带上。Pinia store 只用来存纯前端的本地状态。

**原因：** 一份数据只要有两条获取路径，就必然会出现“顶栏变了、列表还没变”或者两个加载圈不同步的怪象；收拢成唯一
一条路径后，修好一处缓存逻辑，全站所有页面同时受益。如果查询 key 漏掉了某个过滤参数，切换过滤条件时就会直接拿
上一次的缓存顶替，给用户看错数据（TanStack Query、SWR 与 Pinia Colada 官方文档均有此硬约束）。

**本仓库的实现：**
- 优先直接用 SDK 生成好的查询配置和 key 工厂（比如 `getBotsQuery()`）。手写 `useQuery` 时，key 数组第一项用固定
  的业务名，后面跟齐参数，比如 `['bot-settings', botId]`。
- 账号切换不用塞进每个查询 key：在登录、退出登录和遇到 401 鉴权失效时，应用会直接清空整棵内存查询缓存和
  localStorage 里的持久化缓存（`store/user.ts`、`lib/api-client.ts`）。
- 写操作完成后，在 `onSettled` 里把它改动的查询 key 标为失效（`queryCache.invalidateQueries`）。如果某个值刚保存完、
  用户立刻按浏览器刷新就必须看到最新值，再补调一次 `saveQueryCacheToDiskNow()`。
- 所有请求底层都经过 `lib/api-client.ts`，统一挂 Bearer token 和拦截 401。
- 聊天是全站唯一走专用长连接的例外：实时对话内容走 WebSocket，会话列表变动和缓存失效信号走 SSE，统一收口在
  `store/chat-list.ts` 里处理（详见 `references/architecture.md` § 流式传输）。聊天数据只准走这两条通道。

**常见错误：** 在组件里写 `onMounted(async () => { list.value = await getX() })`；把接口拉回来的列表存进 Pinia store；
手写裸 `fetch('/api/…')`；在 `useQuery` 旁边自己又建一个 `loading` ref；查询 key 漏掉了分页或筛选词参数，导致切了
筛选条件画面还不更新。

**边界：** 非后端 API 的特殊传输（比如带实时进度条的大文件上传、请求外部第三方 URL）可以用各自的传输方式，但报错处理
照样要守 U3 的规矩。

**自查方法：** 清楚说出你这份数据对应的唯一查询 key 是什么、哪个写操作会让它失效；挨个拨动页面上所有会影响结果的筛选词、
Bot 或页码，确认查询 key 跟着一起变。

**保证方式：** 机械检查（ESLint 拦截业务代码直接调用裸 `fetch`，存量文件白名单受控）；文字（其余部分，来源：用户确认；查询 key 是否漏掉某个业务过滤参数、写操作该使哪几个关联 key 失效，取决于后端接口契约，静态 AST 无法自动推导）。

### M4. 视觉取值来自档位

**适用场景：** 写任何颜色、字号、尺寸、间距、圆角、边框、阴影、透明度、层级（z-index）、动效时长或字体属性。

**规则：** 每一个视觉数值都必须取自现有 token 或设计档位（scale）里有名字的一档。如果现有档位真没有合适的，先经批准在
`@felinic/ui` 里加好新 token 再回来用。参考外部产品时只学交互思路，所有具体尺寸、色号和间距都要按我们自己的档位和密度
重新换算。动效时长还要守住三条线：高频交互反馈（按下、悬停、聚焦）不超过 **150 ms**；元素收起消失比展开出现更快；超过
**600 ms** 的慢动效只准用于非用户触发的背景氛围动画。

**原因：** 暗色模式漏出刺眼白块、相邻两个按钮悬停深浅不一、页面之间差几个像素怎么都对不齐，全是因为手写了裸数值。每天被点
几十次的高频交互如果动画拖泥带水，累加起来就是明显的卡顿感。上述动效时长底线来自 Atlassian 动效规范（日均触发几十次的高频
反馈压在 150 ms 以内，退场短于进场）与 Material Design 3（超过 600 ms 仅用于无用户输入的背景过渡），负责人于 2026-10-27 确认。

**本仓库的实现：**
- 完整视觉契约见 `packages/ui/AGENTS.md`（§ 三条视觉铁律、§ 脏模式红线与软色阶 Alpha Token、§ 浮层阴影与 5 级 z-index 高度梯、§ 圆角与边框体系）。
  所有 token 只在 `packages/ui/src/style.css` 一处定义。
- 契约守卫脚本（`scripts/check-ui-contract.mjs`，绑在 `mise run lint` 里）会自动拦截 `packages/ui` 里的裸颜色、任意圆角
  和手写阴影；在 `packages/ui` 和 `apps/web` 两边同时拦截文字相关的裸 `px`、裸 `z-index`、手写斜杠透明度和非法颜色函数；
  并在 `apps/web` 里拦截往公共组件标签上硬塞样式的做法。老代码里的历史违规记在 `scripts/ui-*-baseline.json` 里临时豁免，
  新写的代码只要违规立刻报错。
- 注意 lint 脚本目前拦不住 `apps/web` 里写在普通 `div` / `span` 上的裸颜色类名，所以改完页面必须肉眼切一下深色模式自查。
- 动效时长档位见 `packages/ui/AGENTS.md` § 交互反馈、按压缩放与动效档位（脚本暂不自动检查时长）。`@felinic/ui` 里现有的按钮按压弹簧回弹（255 ms）
  和开关松开（160 ms）与 150 ms 档位并存，作为组件库既有设计保留，等下次 UI 大改版时再统一调整；日常在业务层新写的高频反馈
  一律压在 150 ms 以内。

**常见错误：** 直接照抄别家产品的像素值和色号；手写 `bg-white`、`text-foreground/80`、`z-50`；为了突出某张卡片自己挂个
`shadow-md`。

**边界：** 组件完全可以有自己的鲜明特征（比如带立体阴影的滑块圆头、特殊的圆角造型），只要这些特征写成语义 token 即可。

**自查方法：** 跑一遍 `mise run lint` 全绿，且没有往 baseline 文件里偷加豁免，也没有乱加 `ui-allow-*` 注释。新写的过渡动画打开
DevTools 的 Animations 面板看一眼真实毫秒数。

**保证方式：** 机械检查（UI 契约守卫脚本）；文字（脚本未覆盖的部分，含动效时长，来源：用户确认；普通 HTML 元素上的业务条件类名与 CSS 过渡曲线需结合交互角色判断）。

### M5. 修复根因

**适用场景：** 修 bug、修视觉错位或修挂掉的测试与 lint 检查，尤其是只给你甩了一张报错截图或单个复现步骤的时候。

**规则：** 顺着调用链查清楚问题到底为什么会发生，在根源上把它修掉，让同一个根因惹出来的所有同类问题一次绝迹。绝不只在报错的
那一行糊个补丁、拿默认兜底值（`?? fallback`）把异常藏起来，或者为了哄过检查脚本写个特判。

**原因：** 头痛医头、脚痛医脚会把真正的病根留在系统里，过两天换个页面又会冒出来，而且一层叠一层的补丁会让下一个人查问题时
根本看不清真实的数据流。

**本仓库的实现：**
- 同一个病根往往会在界面上同时闹出两三个怪象：只要看到一次操作引发了多处不对劲，先顺着往上游找它们共同的源头（`references/architecture.md` § 页面重构与交接自检流程）。
- 跨模块之间的前提假设，要么用 TypeScript 类型锁死，要么用测试锁死；锁不住的假设干脆删掉——靠写一行代码注释根本约束不住后人。
- 仓库里明确禁止的三种“掩耳盗铃”修法：怕表单被冲掉就把全局后台刷新关了（违背 U2）；嫌页面打开慢就把 `staleTime` 调大掩盖没做
  缓存的问题（违背 U4）；画面切换闪了一下就套个 `setTimeout` 延时遮丑（违背 U5）。
- `ui-allow-*` 豁免注释和 baseline 条目只在真有合理设计理由时才准加，而且必须把理由写清楚（脚本对 `ui-allow-shape` 已强制要求写明理由，其他豁免同样照此执行）。

**常见错误：** 明明上游不该传空值，却在下游顺手写个 `?? ''` 糊弄过去；拿 `!important` 硬顶掉自己项目组件库的样式；公共组件有
毛病不去修公共组件，反而在某一个业务页面里写一段私有 CSS 打补丁；测试挂了直接把断言删掉。

**边界：** 如果真正的根因跨了大领域、或者需要动筋骨做大重构，超出了当前小任务的授权范围，允许先在正确位置做一个最小的安全止血，
但必须在代码注释和交接说明里明确标上“临时止血方案”，并把查出来的根因记下来立项。

**自查方法：** 用一句话清楚回答：“这个问题到底是哪一层为什么引起的？为什么修完这里之后，其他页面不会再犯同样的毛病？”

**保证方式：** 文字（来源：用户确认；区分“根因修复”与“症状补丁”依赖对完整调用链与业务前置条件的理解，任何静态工具都无法自动判定）。

### M6. 保持分发边界

**适用场景：** 改动的代码同时被多个宿主（Web 浏览器端、Desktop 桌面客户端）或多个发行版（开源版 OSS、商业版 Cloud）共用，或者
需要加一段只属于某个宿主/版本的逻辑。

**规则：** 多端共用的代码只写一份，且在任何宿主下都能直接跑通；宿主特有的行为一律由宿主在启动时从外部注入，绝不在公共代码里分叉
复制。开源仓（`felinics/Memoh`）的代码里绝不能混进任何 Cloud 商业版专属逻辑或私有信息。

**原因：** 一旦把页面或 store 复制一份出去改，两边很快就会各自演进、彻底脱节，以后修任何 bug 都得在两边各改一遍。而在开源仓里漏进
Cloud 逻辑，不仅会泄露内部实现，还会在定期把 OSS 合并进 Cloud 子模块时撞出严重的同步冲突。

**本仓库的实现：**
- 业务路由只在 `src/routes.ts` 里通过 `createAppRoutes('web' | 'desktop')` 定义唯一一份；Web 和 Desktop 各自特有的路由守卫留在各自
  的启动入口里。
- Desktop（`apps/desktop`）直接复用 `@memohai/web` 的模块；真需要和 Web 表现不同时，通过扩展 Desktop 启动引导逻辑或增加明确的
  `@memohai/web` 子路径导出来实现，**绝不复制分叉 `apps/web` 的页面**（见 `apps/desktop/AGENTS.md`）。共享 store 一律使用宿主注入的
  router 实例（Desktop 跑的是内存路由 `createMemoryHistory`，不是浏览器 URL 路由）。
- 在组件里需要区分宿主能力时，只读取由外层注入的 `DesktopShellKey`。
- `apps/web` 在任何时候都必须能作为一个纯粹的独立浏览器网页正常运行。

**常见错误：** 在共享页面或组件里手写 `if (isElectron)` 或去嗅探 `navigator.userAgent`；为了改一个小地方把整个 vue 页面复制进
`apps/desktop`；在共享的 Pinia store 里直接 `import router from '@/router'`（这会把 Web 专用的浏览器路由硬拽进 Desktop）。

**边界：** 通过正规注入的开关（如 `DesktopShellKey`）做局部小适配完全合规。

**自查方法：** 凡是动了公共模块、路由或共享 store，在 Web 浏览器和 Desktop 客户端里各跑一遍确认。

**保证方式：** 结构（统一路由工厂、依赖注入 key）；机械检查（ESLint 禁止共享 store 直接 import `@/router`）；文字（其余部分，来源：用户确认；某项功能属于 OSS 通用能力还是 Cloud 专有策略属于产品边界裁决）。

### M7. 性能有预算，失败可追溯

**适用场景：** 新装第三方依赖、写重型组件、渲染长列表、加轮询定时器、写高频输入事件处理函数，或增加新的报错分支。

**规则：** 首屏启动体积和日常交互耗时不能在不知不觉中膨胀；任何报错分支都必须保留足够追查根因的线索。交互与加载速度以 Google
Core Web Vitals 的第 75 百分位（p75）“良好”线为准（桌面端与移动端分开看）：
- **INP（从点下或按键到下一帧画面绘出）**：`≤ 200 ms`
- **LCP（首屏最大内容渲染完成）**：`≤ 2.5 s`
- **CLS（页面生命周期内的意外排版跳动）**：`≤ 0.1`
- **单次输入事件处理耗时**：控制在 **50 ms 以内**（RAIL 模型），算不完的重活拆出去异步做，给浏览器留出余量在 100 ms 内画出反馈帧。

**原因：** 每次顺手在顶层引一个大包、每次多挂一个不暂停的后台轮询，单看只慢了几毫秒，攒半年整个应用就会变得又慢又卡。而把底层报错信息
吞掉的 catch 块，出了线上故障连查都没法查。

**本仓库的实现：**
- 重型库一律按需动态加载（比如 `useShikiHighlighter` 里用动态 `import('shiki')`）；所有路由页面在 `routes.ts` 里全部懒加载。
- 轮询定时器在标签页切到后台（`document.hidden`）时必须暂停，组件卸载时彻底清掉（ui-patterns skill `references/degraded-and-destructive.md`）。
- 条目数量可能无限增长的列表，必须做分页或虚拟滚动。
- 后端返回的规范错误都带着 `request_id`（见 `memoh-error-handling` skill）；在前端捕获、包装或往上抛错误时，必须保留原始错误对象，别把
  `request_id` 弄丢了。
- **当前缺口**：前端目前还没有接入自动采集真实用户性能指标的埋点（未装 `web-vitals` 或 `PerformanceObserver`），也没有给构建产物设硬性的
  体积报警线，界面报错时还没把 `request_id` 亮出来。在补齐自动采集前，涉及复杂交互的改动直接用 Chrome DevTools 的 Performance 面板录一次；
  引新包时对比改动前后 `pnpm --filter @memohai/web build` 的产物体积，确保不劣化。

**常见错误：** 为了某一个低频设置页，在入口文件顶层同步 `import` 几百 KB 的图表或编辑器大包；写了 `setInterval` 却不监听页面可见性；
几千条消息或日志不虚拟化直接一次性 `v-for` 塞进 DOM；在输入框的 `@input` 里同步跑复杂的正则或大数组遍历。

**自查方法：** 打开 DevTools Performance 面板录一遍你改动的交互：确认 INP 不超过 200 ms，输入事件回调里没有超过 50 ms 的长任务（Long Task）。
对比改动前后的构建产物大小，并看一眼首屏 Network 瀑布流。

**保证方式：** 文字（来源：用户确认；运行时帧率、INP 耗时与长列表数据规模属于动态性能表现，静态 AST 无法直接测出毫秒数）。

### M8. owner 保持可修改

**适用场景：** 准备给现有的共享组件（owner）加新 prop、加特判分支、在外面绑 class 覆盖它的样式；或者发现某个共享组件已经改不动了。

**规则：** 一个共享组件（owner）只管一个清晰的概念。当新需求必须靠“再加一个 prop、再加一个 `v-if` 特判、或者在外面绑 class 硬盖”才能塞进去时，
先停下来想清楚：它到底是同一个概念下的正常档位变体，还是其实已经是另一个概念了？如果是另一个概念，要么拆成独立的新组件，要么在页面层拿基础
零件重新拼，**绝不继续往原来的 owner 里硬塞开关和特判**。对职责已经乱成一团的老 owner，按“先冻结 → 再分流 → 最后删旧代码”分步清理，每次只走一小步，
保证随时能安全回退。

**原因：** 共享组件最大的价值就是“改一处，全站生效”。但每往里多塞一个布尔开关或特判，里面的状态组合就会翻倍增长，直到最后谁也不敢碰它——大家为了
不惹祸，又开始在页面里复制粘贴各写各的，彻底退回 M2 最怕的“到处是重复代码”。

**本仓库的实现：**
- **组件开始腐化的危险信号**：外面的页面不得不绑一堆 class 去改它的样式（脚本的 `scripts/ui-app-baseline.json` 里记着各文件的违规存量）；某个 prop
  或分支全站只有唯一一个调用方在用；有个叫 `variant` 或 `mode` 的属性，传不同值时居然会切出两套完全八竿子打不着的 DOM 布局；每次改它哪怕一行代码，
  都得提心吊胆去手测五六个页面。（注：`@felinic/ui` 原子组件因为要原样透传底层 Reka UI 的全部原生属性，props 数量多是正常的，不算腐化。）
- **清理腐化组件的标准五步法**：
  1. **冻结接口**：立刻停止往这个老组件里加任何新 prop 或新分支；新需求一律按上面的原则拆出去或用基础组件拼。
  2. **盘点分类**：把现有的每个 prop、特判和外部样式覆盖归进四类：同概念的正当变体、混进来的另一个概念、本来该收进 Token 档位的数值（M4）、纯粹的历史包袱。
  3. **拆解瘦身**：给最常见的标准用法留一个带默认值的清爽入口；少见的定制需求让调用方直接拿 `@felinic/ui` 原子组件和 composable 自由组合，不再在顶层大组件上
     开后门；混进来的另一个概念直接独立成新 owner。
  4. **分批迁移**：给旧属性标上 `@deprecated`（写在 TS 类型上，并在 `ui-owners` 字典里注明），用基线脚本拦住新代码继续用旧属性；老调用方分批提纯重构 PR 迁走，
     机械替换直接写脚本跑。
  5. **彻底清理**：等旧属性的调用方清零后，删掉旧代码和对应的 baseline 豁免。
- 上面每一步都单独开 issue、单独提 PR，绝不把“顺手重构公共组件”混在业务功能 PR 里一起交（D1）。

**常见错误：** “我就加一个布尔 prop，最快！”；在页面里绑 `class="!p-0"` 硬改公共组件的间距；嫌改公共组件麻烦，干脆拷一份出来改名；一个 PR 同时重写公共组件又改十几个业务页面。

**边界：** 同一个概念下的正常视觉档位（比如按钮的 `size="sm" | "lg"`、色调 `variant`）用 prop 表达天经地义。拆分时同样守住 M2：只按真实的业务概念拆，拆出来的每一块都要能用一句话说清它代表什么。

**自查方法：** 加任何新 prop 之前，先用一句话写出来：“这个 prop 代表【某概念】的哪一种通用变体？”如果写出来是“当在某某页面时隐藏右边的按钮”，那就绝对不该做成 prop。

**保证方式：** 文字（来源：用户确认；一个新 prop 属于“同概念的正当档位”还是“混入了另一个概念”属于领域建模判断，无法由静态语法直接判定）。目标：机械检查（用基线脚本拦截 `@deprecated` 属性的新增调用），并在 `ui-owners` 字典里维护组件状态标注（`[稳定]` / `[弃用中]`）。

## 3. 完成的定义

不管是人写的还是 agent 写的，交活时都用下面同一把尺子量。通用的提 PR、截图和 QA 披露流程见仓库根目录 `AGENTS.md`，这里只列前端特有的四条底线：

### D1. 只改动需求范围内的内容

**规则：** 提交的 diff 里只准包含完成当前需求必需的改动；顺路发现的其他老问题记进交接说明里另行处理。如果是重构任务，除非需求明确让你改行为，否则重构前后的外部行为必须完全一致。

**原因：** 顺手塞进来的无关改动不在 Reviewer 的预期视线内，最容易神不知鬼不觉地把别的功能改坏。

**常见错误：** 写业务需求时顺手升了依赖包版本；修单个页面时顺手改了公共组件的默认间距；看着某个旧文件名不顺眼顺手把它重命名了。

**边界：** 为了守住本规则而必须做的联动改动（比如按 M2 把页面里调好的修复沉进共享 owner）算在合理范围内，在交接说明里讲一声即可。

**保证方式：** 文字（来源：用户确认；某行改动是否属于当前需求范围需要对照具体 issue 目标判断）。

### D2. 逐项列出行为、外观和默认值的改动

**规则：** 在交接说明和 PR 描述里，把所有用户看得见的变化、交互行为的变化、默认值的变化一条不落地列成清单——哪怕你觉得“这改得理所当然”也要写出来。关掉某个功能、改了默认停留时间、新加了拦截守卫，必须逐条报备。

**原因：** 审代码的人只能审他知道的改动；没写进清单里的行为变化，十有八九会漏过审查直接上生产。

**保证方式：** 文字（来源：用户确认；PR 描述是否覆盖了全部行为变化需对照 diff 语义核对）。

### D3. 声明不超过证据

**规则：** 验证过了什么就只说什么，并且写清楚是怎么验证的：`pnpm build` 能过只证明语法能打包，绝不等于页面能正常用；静态截图只证明截下来的那一瞬间画面长这样，绝不等于后端逻辑对；agent 自己跑的浏览器检查必须如实标明是 agent 自测，绝不能勾上“人工 QA 已通过”。

**本仓库的实现：** 启动开发环境、操作真实界面和截图取证按根目录 `AGENTS.md` § Mandatory Runtime and UI Verification 执行；人工 QA 复选框按 § Pull Request QA Status 执行；页面布局与视觉还原按 `references/architecture.md` § 页面重构与交接自检流程 及 `ui-patterns` skill 逐项核对。

**保证方式：** 文字（来源：用户确认；交接声明与真实测试证据是否匹配需在 Review 时核验）。

### D4. 检查全部通过；每个豁免都写明理由

**规则：** 交活前 `mise run lint`（含 ESLint 与 UI 契约守卫脚本）、TypeScript 类型检查和相关测试必须全绿。任何一处豁免（`eslint-disable`、`ui-allow-*` 注释、baseline 条目）都必须在代码旁边写清楚为什么非豁免不可，理由要让完全没看过这次对话的同事也能一眼看懂并信服。

**保证方式：** 机械检查（`mise run lint`、`check-ui-contract.mjs` 强制检查豁免理由非空；来源：用户确认）。
