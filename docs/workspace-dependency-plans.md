# 工作区依赖计划与 Requires

Supermarket 的 `dependency.requires` 由 OSS 的 `workspacedeps` 层执行。App 安装、恢复、选择性更新和独立依赖安装、更新、重装、回滚、移除共用同一套计划。计划只解释依赖 ID，不做版本范围求解，也不会顺便升级已有前置工具。

## 预览与确认

`POST /bots/{bot_id}/dependencies/plan` 接受根操作列表；`POST /bots/{bot_id}/apps/prepare` 根据不可变 App release 和操作选择生成同一种计划。响应列出拓扑顺序、直接根、依赖原因、每个节点的来源、registry、revision、manifest digest，以及实际执行脚本预览。已有可用的镜像、用户或 managed 命令标为复用；安装记录的 `installed` 标签不能替代工作区探测。

服务端把计划写入 `bot_dependency_plans`。变更请求携带 `plan_id`，每个节点执行前从已验证的不可变定义缓存加载自己的 publication；客户端不能通过提交脚本文本或自行编辑节点列表改变执行内容。不同 HTTP 请求和 Server 重启不会把计划换成最新 revision。App release 本身也需要保留预览返回的 revision。

当定义缺失、退役、根动作或版本不匹配，或者原先复用的工具已经丢失或其 managed publication 已改变时，操作拒绝执行并要求重新预览。已被其他操作安装好的前置可直接复用。一个已完成的更新节点具有持久化计划身份，同一计划重试不会再次运行它。

Web/desktop 客户端需随服务端更新。旧客户端仅提交根 definition revision 的安装请求会收到要求重新准备计划的错误；服务端不提供绕过完整确认的兼容执行路径。聊天中的 App 管理工具仍先经过现有 Manage 审批，只是审批内容扩展为完整依赖计划；discovery、设备码登录、普通聊天和更新检查不会隐式安装。

## 执行、并发与恢复

计划先用现有 catalog 校验器验证完整图，再探测工作区、校验平台和脚本能力，最后才开始安装。共享节点去重，每个前置的脚本结果、state.json、shim、安装记录和引用提交完成后才运行下游。失败阻断下游，独立分支可以继续；成功前置保留，App 延续 partial 语义。

`bot_dependency_graphs` 提供 team + bot 范围的持久化准入。一次短事务锁定图记录并检查未完成的节点操作，领取 60 秒租约；持有者每 10 秒续约。下载期间没有打开的数据库事务。另一个 Server 遇到冲突直接收到 `ErrBusy`，不会排队。每个节点仍使用原有 `ClaimOperation`、flock、runner、manifest timeout、receipt、`FinishOperation` 和 reaper。

节点 claim 以及 App 引用写入校验图的所有权。过期持有者不能继续写引用或领取新节点。即使图租约过期，未确认结束的节点仍阻止新的图变更；reaper 按原协议验证或 fence 该节点。成功 receipt 的安装结果与 Requires 引用在同一次数据库语句中提交，因此另一台 Server 恢复结果也不会遗失关系。

SSE 提供当前节点、动作、状态、依赖原因，以及失败节点、根、路径、阶段和 operation ID。HTTP/SSE 错误仍通过统一 apperror 映射，底层诊断只写服务端日志。

## 引用与卸载

图中每个父依赖分别保存已安装定义的 Requires、尚未完成的引用意图、显式安装标记和完成计划身份。App 的直接依赖继续保存在原 App 引用表中，不把传递依赖伪装成 App 的直接依赖。

计划在运行任何节点之前持久化待完成引用。失败更新保留旧版本关系；目标提交成功才切换引用。显式安装标记只能保留或升级，不能被后续自动前置安装降级。App 引用写入、安装、更新与删除都遵守同一工作区准入规则。

显式卸载 App 时，共享引用、其他依赖的 Requires、待完成引用、显式用户安装和未知历史关系都会阻止自动删除工具。移除 managed overlay 保留镜像基线与用户文件。卸载脚本取自实际已安装的不可变定义。卸载确认绑定 App revision 及所观察到的依赖 revision；审核期间更新了某个依赖时，需要重新预览。可选的自动 App 清理仅覆盖原预览中确认的 App revision。

本版不做依赖垃圾回收：卸载父依赖后保留无引用的自动前置；App 更新成功后释放不再需要的直接引用，同时保留对应工具，避免在确认安装计划时执行额外的卸载脚本。之后可通过显式管理操作安全删除。

独立工具的移除通过 `POST /bots/{bot_id}/dependencies/{dep_id}/remove` 提交已确认的移除计划。工具仍被引用时，预览和执行都会拒绝并列出依赖者；预览后出现的新引用也不能绕过这一检查。Web 的工具详情提供对应入口。

## 旧数据与迁移

迁移 `0160_dependency_plans` 增加计划和图存储，启用 FORCE RLS，并使用 `(team_id, bot_id)` 外键保持工作区隔离；同时更新完整初始 schema。迁移不执行脚本，也不删除已有工具。

旧安装首次参与图变更时，从记录中的确切 revision / digest 和已验证缓存重建关系。找不到可靠历史时保留工具并阻止可能破坏其他依赖的删除，要求先协调或修复安装。不能拿今天最新的 Requires 猜旧图。旧安装缺少安装原因时保守视为显式保留。

回滚必须取得历史定义和对应工作区版本目录；历史信息缺失时明确拒绝。检查更新保持只读，脚本前置丢失时返回待修复状态。

## 验证

关键自动化覆盖在 `internal/workspacedeps/plan_test.go` 和 `graph_pg_integration_test.go`：真实 bridge/runner 脚本验证链与菱形顺序、父命令调用、共享节点去重、预检失败、文件丢失、不可变定义、独立失败分支、v1→v2 引用切换、重试、跨 Service 竞争和旧历史保留。PostgreSQL 测试检查跨 Server 准入、过期所有者 fence、receipt 原子提交、计划持久化和作用域隔离。

现有 recovery/lifecycle、App 清理和 HTTP 权限测试继续覆盖断连、服务关闭、恢复与公开错误。真实 docx 验收必须单独记录运行镜像、工作区命令基线、API/SSE、转换结果与卸载保护；其他环境中的脚本批测不能替代这些证据。

不覆盖自动垃圾回收、版本范围求解、批量升级所有前置。未实际验证的平台必须在交付说明中列明。

确认窗口保留既有 DialogPanel / DialogBody / DialogFooter；脚本详情复用原查看器。

```text
安装 / 更新 / 恢复 / 回滚标题
┌ 可滚动内容 ───────────────────────────┐
│ 版本或操作选择（适用时）               │
│ 依赖安装计划                          │
│   工具名与所需原因    安装/复用  查看脚本│
│   ……                                  │
└──────────────────────────────────────┘
                              取消  确认
```

窄屏下行内容堆叠，标题与确认按钮留在滚动区域外。深色与中文布局使用现有设计 token。
