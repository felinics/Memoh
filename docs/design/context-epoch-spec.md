# Context Epoch 技术规格

这份文档规定系统**必须遵守的行为**。为什么这么设计，看 [cache-stable-context-rfc.md](./cache-stable-context-rfc.md)；两份文档冲突时以这份为准。

## 这份文档在管什么

Memoh 每一轮对话都会把系统提示、历史消息、这轮的新输入拼成一份完整的请求发给模型。模型服务商有个计费规则：这次请求的开头如果和上次一模一样，相同的部分只收大约一成的钱（缓存价）；开头只要变了一个字节，从那里开始全部收全价。

这份规格管的就是一件事：**怎么安排上下文，让这个"开头"尽量不变，并且每次不得不变的时候都有记录。**

## 基本概念

- **稳定部分**：请求的开头部分，包括系统提示和已经压缩好的历史摘要。这部分的字节是我们承诺"能不变就不变"的。
- **变动部分**：稳定部分之后的内容，包括还没压缩的原始消息和这轮新进来的输入。这部分随便变，不影响缓存。
- **摘要段**：一段压缩好的历史，落盘之后就不许再改。多段摘要按时间顺序接成一条链。
- **epoch**：稳定部分的版本号。稳定部分只要变了，epoch 就加一。只能加，不能减。
- **anchor（书签）**：一个位置标记，表示"历史从这里开始读"。只能往前挪，不能往后退。

为什么要把请求分成稳定部分和变动部分：压缩不可避免（对话会无限变长），而压缩一定会改变它覆盖的那部分内容。我们消灭不了"变化"，只能决定变化**发生在哪里**和**多久发生一次**。把变化赶到变动部分去，让稳定部分尽量长、尽量不动，缓存命中率就上去了。

## 系统要记住的状态

每个（对话线程 × 机器人）组合存一份：

```go
ContextEpochState {
    Epoch        int        // 稳定部分的版本号，只能加
    Anchor       MessageRef // 历史从这里开始读，只能往前挪
    SegmentCount int        // 当前有几段摘要
    ToolsetHash  []byte     // 这个 epoch 里钉死的工具列表
    Budget       int        // 这个 epoch 里钉死的历史预算
}
```

实现对照（Context Epoch PR 系列落地形态）：

- `Epoch`/`Anchor`：`bot_sessions.metadata.context_epoch`（`epoch`、`anchor_created_at_ms`、`anchor_message_id`、`last_reason`），守卫式 SQL 单调推进。
- `Budget`：`budget_tokens` 钉在同一状态里（首钉赢，跨推进存续）。
- `SegmentCount`：不落库为字段，由压缩层按活跃段链长度实时计数，超过上限 K=8 触发合并。
- `ToolsetHash`：不落库为字段；工具列表的稳定性由网关兜底保证（刷新失败沿用上次成功列表，降级列表不缓存）。
- 另有 `prefix_hash`（规范"怎么监控"一节的规则 1 记账）：钉住 epoch 内首次观测的监控哈希，口径 = 渲染后的系统区 + 模型身份；不一致触发 `context_epoch_prefix_drift` 告警。

几条规矩：

- 状态按（线程 × 机器人）分开存。多个机器人在同一个讨论线程里时，各管各的，互不干扰。
- 改状态和追加摘要段必须是同一次数据库写入；做不到的话，加载时要能检测出不一致并修复。崩在中间不算正常状态。
- 系统提示的所有内容（模板、人格、技能、记忆概况、工具列表）只能由这份状态和机器人配置决定，**不许**依赖当前时间、缓存 TTL、随机数、这轮请求的内容。

## 必须遵守的规则

**规则 1：同一个 epoch 里，稳定部分一个字节都不能变。**
检查方法：每轮给稳定部分算一个哈希（`stable_prefix_hash`），同一个 epoch 里这个哈希必须一直相同。

**规则 2：书签只能往前挪。**
读历史的起点不许往后退。

**规则 3：摘要段落盘后不许改。**
不许融合、不许重写、不许就地编辑。要改旧摘要，只能走"合并"（见下文），而合并会推进 epoch。
检查方法：沿用现有的 coverage 内容哈希校验。

**规则 4：同一个 epoch 里，历史预算不变。**
这轮新输入长一点，历史预算不许因此变小。要收紧预算，先推进 epoch 再说。

**规则 5：没压缩的原始消息不能无限多。**
设一个上限 `rawThreshold`。超过就触发压缩。这个上限同时也是压缩时缓存失效量的上限。

**规则 6：稳定部分的每次变化都必须留下记录。**
记录里写清楚 epoch 从几变成几、原因是什么。不允许出现"开头变了但查不到为什么"。

**规则 7：稳定部分只放不常变的内容。**
任何内容按它的变化频率决定放哪：很少变的放稳定部分，经常变的放变动部分。比如记忆概况如果每天都更新，就不许放稳定部分。

## 只允许对上下文做这四件事

除了下面四种操作，任何代码路径都不许改动请求内容。发现第五条路径，就是 bug。

| 操作 | 什么时候发生 | 做了什么 | 对缓存的影响 | 最多多久一次 |
|------|-------------|---------|-------------|-------------|
| **正常对话** | 每轮 | 新消息追加到变动部分末尾 | 无影响，开头继续命中 | — |
| **压缩成段** | 没压缩的原文超过 `rawThreshold` | 最旧的一批原文压缩成一段新摘要，接在链尾 | 这一段原文位置的内容变了，失效量 ≤ `rawThreshold`；它之前的系统提示和旧摘要段继续命中 | 每轮最多一次 |
| **合并旧段** | 摘要段数超过 K（建议 8） | 最旧的几段合并成一段；书签往前挪；epoch 加一，原因记 `segment-merge` | 整个稳定部分失效一次 | 平均每 K 段最多一次 |
| **显式翻篇** | 预算要收紧 / 用户切断历史 / 换模型 / 工具集变了 / 人工触发 | 更新对应字段，epoch 加一，写明原因 | 稳定部分失效一次 | 同一件事不许连续触发两次 |

"稳定部分整体失效"只允许来自最后两行。别的地方出现，就是 bug。

## 外部事件怎么处理

有些事情不受我们控制：模型故障切换、服务重启、用户改了机器人配置、MCP 工具列表真的变了。这些事件发生后，必须走"显式翻篇"记录在案，**不许**不声不响地反映到请求里。

特别地：MCP 工具列表刷新失败时，继续用上次成功的那份，不许因为这轮没拉到就临时换一份。

## 怎么监控

每轮把 `(epoch, stable_prefix_hash, final_input_hash)` 存下来（包括服务重启后的第一轮）。

告警规则：

- 同一个 epoch 里 `stable_prefix_hash` 变了 → 违反规则 1，告警。
- epoch 变了，也有对应的原因记录 → 正常，只计数。
- epoch 变了，但查不到原因记录 → 违反规则 6，告警。

两个验收指标：

- 稳定部分命中率 = 缓存命中的 token ÷ 稳定部分的总 token，目标 ≥ 95%。
- 整体失效的频率 ≤ 每 K 段一次 + 显式翻篇的次数。

统计时要按"相邻两轮的时间间隔"分开看：服务商缓存本身有过期时间（几分钟到几小时），隔太久的对话本来就会失效，这部分不该算在我们头上（见"已知局限"第 1 条）。

## 代码接口（已实现）

```go
// internal/chat/contextepoch

// 按书签读历史，取代按"24 小时前"读：字节预算 + 书签锚定，预算挤压到
// 更老行时记录一次 reason="budget" 的显式推进。锚点定位失败必须报错，
// 不许悄悄返回空历史。
func (s *Store) LoadWindow(ctx context.Context, sessionID, path string, measure, load ...) ([]message.Message, error)

// 原地翻篇的统一入口。原因必须属于审计词表（ValidAdvanceReason），每次
// 调用都留下 (from_epoch, to_epoch, reason) 审计日志。移动锚点的推进
// （budget 滑窗、segment-merge）走各自的原子 SQL 写。
func (s *Store) AdvanceContextEpoch(ctx context.Context, sessionID, path, reason string) (State, error)

// 首钉赢的记账写入：epoch 内历史预算（规则 4）与监控哈希（规则 1）。
func (s *Store) PinBudget(ctx context.Context, sessionID string, budgetTokens int64) (State, error)
func (s *Store) PinPrefixHash(ctx context.Context, sessionID, prefixHash string) (State, error)
```

装配层（`internal/contextview` 的 `RunConfigProvider`）是拼稳定部分的唯一地方。像"MEMORY.md 该重写了"这类开关，允许在一个 epoch 里决定"渲染还是不渲染"，但不许在一个 epoch 里改写已经渲染过的字节；开关翻转本身按翻篇记账。

## 和现有机制的关系

- **内存安全（CM-ADM-001）**：不动。历史加载照样按字节预算截断、照样先计量后加载。书签取代的只是"24 小时"这个时钟，预算的规矩一条不少。
- **压缩的血缘和并发控制**：artifact、coverage 哈希、CAS、reclaim 全部保留。变的只是压缩产物的形态（从"每次融合成一整段"变成"一段一段接龙"），不是这些机制。
- **老数据**：已有的融合摘要照常能读，不用迁移数据。
- **讨论模式**：它已经用 `discuss_since` 做书签式加载了，统一到 `ContextEpochState` 就行。顺手把它的 CacheNever 标签修掉——它标"永不缓存"是因为位置在中间，但它的字节其实是稳定的，这个标签目前让它的缓存白扔了。

## 轮内和轮间的边界

这份规格管的是轮与轮之间的上下文（落盘历史怎么投影进请求）。一轮之内的事——工具结果累积、步级修剪、预算恢复——由对话循环自己管（现状：工具输出源头截断、旧工具结果换占位摘要、顶到预算时重排版面）。交界处的三条规矩：

1. **轮内只许动变动部分。** 步级修剪和预算恢复只许裁剪变动区；不许在轮内改写稳定部分。预算自救如果非要动稳定部分，必须按翻篇记账（记 `budget-recovery`），不许悄悄改。现状的重排版面会改写历史区，实现 PR 1 时必须一起收编。
2. **轮内修剪的产物一旦落盘，同样不许再改。** 规则 3 对它一样有效。占位符文本必须是消息内容的确定性函数（即使将来带上回溯指针，指针也要由消息 ID 派生），保证跨轮字节稳定。
3. **轮内修剪会让同一轮后续步骤的请求前缀失效。** 这是步与步之间的缓存问题，这份规格不管，但长任务里这也是真金白银，改轮内策略时要把这笔账算进去。

## 已知局限

1. **服务商缓存会过期。** 两家主要服务商的缓存都有时间限制。两轮对话隔得太久（几十分钟以上），缓存本来就没了，这套架构帮不上也不添乱。收益集中在活跃对话和讨论模式这种高频场景。
2. **稳定部分不是免费的。** 命中也要收一成的钱。书签永远不挪，等于老摘要每轮都在交"保管费"。所以合并旧段不只是收拾屋子，也是省钱；K 和 `rawThreshold` 应该用真实的 token 单价算出来，不能拍脑袋。
3. **真有什么内容就是经常变**（比如机器人每天重写记忆概况），按规矩每次都要翻篇记账——这不会让缓存更省，只是让变化变得可见。正确的做法是靠规则 7 把这种内容挪到变动部分，而不是靠记账。
4. **系统提示里可能藏着时间相关的字段**（当前时间、日期、随机 ID）。只要有一个，规则 1 立刻破功。动手实现前，先把所有系统段的字段逐个查一遍。
5. **监控的哈希口径要定义清楚。** 如果算哈希时混进了每条消息的时间戳、ID 这类每轮都变的字段，会每轮都报警，等于没报。

## 明确不做的事

- 不做跨会话、跨机器人的缓存共享。开头里有人格和锚定内容，不同会话几乎不可能有相同前缀。
- 不追求"上下文永远不变"。变化消灭不了，这份规格只保证：变化发生的位置尽量靠后、频率有上限、每次都有记录。
- 不动服务商适配层（Anthropic 的缓存断点、`prompt_cache_key` 路由）。审过了，是对的。
