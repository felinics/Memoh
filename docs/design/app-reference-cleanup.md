# Apps 引用清理：目标、当前修复与后续路线

## 问题与归属

App A 和 B 共用依赖或连接器时，A 更新可能不再需要该资源。原实现查询共享引用失败后仍按空列表判断，进而删除 B 正在使用的资源。外部删除或引用删除失败也只记录日志，最终仍发送成功事件。

该问题在 OSS 的 Apps 服务内，与工作区 provider 无关。Cloud PR [#324](https://github.com/felinics/Memoh-Cloud/pull/324) 在同步这套实现时发现它；修复先在 OSS 完成，Cloud 再同步并验证其租户与 E2B 边界。

## 当前补丁的目标与实现

安全条件：**查询失败不代表没有引用；未完成的清理必须保留恢复依据。**

1. 从数据库读取该 App 的持久化引用，与本次发布的 release 比较，得到待清理项。新旧 release 相同也不能直接认为清理已经完成。
2. 开始清理前，完成所需的依赖共享引用查询。只有需要处理的依赖才查询共享关系；全部保留的 release 不需要额外工作区探测。
3. 对没有其他 App 引用的依赖，要求工作区处于运行状态且探测成功。原生工作区停止时，按安装步骤的方式先启动再探测，不把"工作区停止"当作失败；工作区未创建、远端 target 离线、探测失败或依赖有进行中的操作时，保留引用并报错。目录中已不存在的依赖没有可删除的内容，只删引用。
4. 被其他 App 引用的依赖只解除引用；需要物理删除的依赖先执行删除，确认成功后再删引用。外部调用或引用写入失败就停止，保留该项及后续未处理引用。
5. 连接器引用只解除，不吊销 Bot 级连接。更新是"换版本"的动作，不表达"断开账号"的意图，而且 App 安装时认领的连接可能是用户在 App 之外授权的。吊销只发生在两处显式动作：卸载 App（带预览确认）和应用连接器子项上的"断开"（`DELETE /bots/{bot_id}/connectors/{connection_id}`），后者吊销凭据并清空所有引用它的 App 的连接，需要该连接的 App 回到 `partial`。
6. 清理属于 materialize 的完成条件，Install、Resume 和 Update 共用此逻辑。错误通过已有错误事件返回，并持久化为 `failed` 与 `last_error`；成功事件仅在清理之后发送。
7. `last_error` 与步骤消息只保存公开描述：错误目录里的公开文案、哨兵错误文本、上游 HTTP 状态，或统一的 `internal error; see the Server log`。数据库、bridge 和第三方服务的原文只进 Server 日志。`partial` 状态下依赖安装脚本的诊断文本仍按原样保留，用户需要它排错。
8. 重试重新读取持久化引用。新服务实例也能从现有记录继续，不依赖首次请求中的旧引用切片。已确认不存在的依赖可以补删引用，无须重复执行卸载脚本。同版本且状态为 `installed` 或 `partial` 时不重新发布 Skills。

本次使用现有表、状态和事件，没有新增迁移或后台服务。连接器 `DELETE` 在远端撤销后，通过一条 SQL 同时清空该 Bot 的 App 引用、将必需连接的 App 降为 `partial`、删除本地绑定。任一数据库步骤失败就整条回滚并保留绑定，重试可把远端 404 视为成功后继续完成本地清理。移除了 Handler 中尽力而为的 `UnlinkConnection` 调用。使用已有 `failed` 表示发布后的清理失败，意味着 Skills 可能已经是新版本；这里没有承诺整个 App 更新具备原子回滚。

## 借鉴的部分

- Nix [GC roots](https://nix.dev/manual/nix/2.34/package-management/garbage-collector-roots)：资源是否保留取决于明确的引用关系。当前补丁保留未完成的引用，避免丢失清理依据。
- Nix [删除前事务检查](https://github.com/NixOS/nix/blob/d262d70a49e3e303151831cf268a7241abe85ae0/src/libstore/local-store.cc#L1416-L1439)：取得完整、可信的引用信息是删除的前提。当前补丁先修正查询错误语义，尚未实现 Nix 的事务删除保护。
- Nix [临时 roots 与删除同步](https://github.com/NixOS/nix/blob/d262d70a49e3e303151831cf268a7241abe85ae0/src/libstore/gc.cc#L84-L158)：安装过程也要保护资源。后续需要让新增引用和删除经过同一个协调入口。
- Kubernetes ownerReferences 与 finalizer、apt 与 Homebrew 的 auto/manual 标记：引用图的变更是即时且便宜的，物理回收是另一个幂等、可延迟的过程。Zapier 与 Nango 把连接当作独立于消费者的一等资源，删除永远是用户显式动作。这是连接器只解引用的依据，也是后续把"释放引用"与"物理回收"拆开的方向。

Nix 使用本地 store、SQLite、文件锁和 socket。Memoh 包含远端工作区和第三方连接器，应借鉴保护条件与恢复机制，不能把本地锁直接当成跨 Server 的删除协议。

## 本次未解决的边界

- **跨 App、跨 Server 的引用竞态仍然存在。** 当前锁只覆盖一个 App，预读共享引用不是并发删除权。A 预读后 B 新增引用的窗口，需要后续资源级协议修复。
- 完整卸载现在遇到组件删除、引用删除、Skills 清理或安装记录删除失败时保留记录并返回失败；恢复后可重新卸载。已完成的外部动作不会整体回滚，因此失败期间 App 可能只有部分组件可用。可选自动安装 App 的失败也会阻止父 App 报告完成。
- 现有 Upsert 仍提前记录目标 release。重试失败状态会重新 materialize，但尚未分离目标版本、已发布版本和回滚版本。
- 用户主动安装、已启用 Agent、依赖之间的传递关系，应分别明确是否构成保留根。当前补丁仍采用已有 App 引用和来源判断，不改变资源所有权产品规则。
- 更新后不再被任何 App 引用的连接会作为 Bot 级授权保留，直到用户断开或最后一个引用它的 App 被卸载。它不再出现在应用列表里，只在聊天输入框的连接器菜单可见；后续需要 Bot 级连接列表或在卸载预览中提示。
- 远端 target 离线时无法从 Server 侧启动工作区，只删依赖的更新会失败并保留引用；后续用"待回收"引用状态解决。
- 外部调用成功、数据库确认失败时可能重试删除；依赖探测和连接器已有 NotFound 处理支持部分恢复，但不构成跨系统 exactly-once 保证。

## 后续路线

### 1. 引用释放与物理回收分离（OSS）

把引用释放与物理回收分离，但不能只锁各 App 自己的引用行。依赖需要按 `(team, bot, workspace_target, dependency)` 维护共同的资源记录，新增引用、安装占用和删除都通过同一个入口。在短事务里确认保留根与引用并取得持久化删除 claim；外部执行在事务外运行。资源进入 `deleting` 后，新引用必须等待或收到可重试冲突，不能直接翻回 `active`。现有脚本 operationID 保护脚本执行，不自动保护 App 的引用写入。

回收结果未知时保留 claim 并核对实际状态，不能只按超时接管。回收器可在更新结束、工作区恢复运行或维护周期中触发；停止的工作区不必为了回收而启动。这是跨 Server 共用的数据库协调协议，仍需单独实现和并发验收。

连接器引用加 `origin`（`app` 或 `adopted`）：认领来的连接只解引用；App 自己创建的连接可在最后一个引用释放后由回收器吊销，允许失败重试。

### 2. 明确保留根与发布状态（OSS）

评估用户主动保留、Agent 所需依赖、传递依赖和安装中占用；资源无人引用后进入可回收状态。评估目标 release 与已发布 release 分离，以及按版本保留文件的发布/回滚流程。前端把 `failed` 收窄为"Skills 未发布"，`installed` 且带 `releasing` 引用的 App 显示"待清理"标记而不是重试按钮。

### 3. Cloud 同步与验收

OSS 修复合并后同步到 #324，保持 Team 上下文、RLS 和 provider-neutral workspace client。若后续增加迁移，按 Cloud 已占用编号调整并重新生成 SQLC。Submodule PR 合并后由已有 Action 更新外层 gitlink。

真实验收覆盖两 Team、两个 workspace target、E2B 暂停/恢复、Server 中断、连接器断开失败和重试。Cloud 专属执行和隔离测试不能替代 OSS 的资源生命周期回归。

## 验证要求

- 查询自身引用或共享依赖引用失败时，零资源删除且恢复引用保留；恢复后仍保护另一个 App 的引用。
- 外部删除或删除引用失败时，操作失败且没有提前的 `done`；重建服务实例后可以继续。
- 工作区未创建、远端离线、探测失败、依赖正在操作或启动失败时，不依据不完整信息清理；原生工作区停止时先启动再清理；依赖已从目录下架时只删引用。
- 同版本 Update（`installed` 或 `partial`）、UpdateSelection 重试和 Resume 均能处理残留引用；`partial` 不重新发布 Skills。
- 更新只解除连接器引用，连接保留且未被吊销；断开连接后引用被清空，需要该连接的 App 回到 `partial`。
- 失败后的 `last_error` 与失败步骤消息不包含注入的底层错误原文；哨兵错误保留其文本。
- 成功清理后只有一个最终 `done`，失败路径没有 `done`。

这些是服务层故障注入要求，不代表已经完成真实工作区、第三方授权或人工 QA。资源级并发协议完成时还必须加入确定性并发和数据库集成测试。

本次还将英文 Settings 导航及市场标题从 `App Store` 恢复为 `Supermarket`，中文翻译保持不变。

## Web 失败恢复入口

断流后的 remove 对账仅在安装记录消失时认定卸载完成。记录为 `failed` 时展示 `last_error` 并保持错误状态；记录仍为 installed/partial 时继续确认，不能推断删除成功。当前进度弹窗保留原始 action，因此它的重试仍继续 remove。

持久化的 `failed` 尚未区分安装、更新和卸载。列表及详情不再把 materialize 标为通用“重试”，而是明确提供“恢复安装”和可见的“卸载”；提示恢复安装可能重新安装已移除的组件。服务端卸载失败的公开描述包含 `App removal failed`，前端不解析错误文案来猜操作类型。后续应将失败操作类型与恢复目标持久化，再自动选择对应重试。
