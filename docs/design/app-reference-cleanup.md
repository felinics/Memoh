# Apps 引用清理：目标、当前修复与后续路线

## 问题与归属

App A 和 B 共用依赖或连接器时，A 更新可能不再需要该资源。原实现查询共享引用失败后仍按空列表判断，进而删除 B 正在使用的资源。外部删除或引用删除失败也只记录日志，最终仍发送成功事件。

该问题在 OSS 的 Apps 服务内，与工作区 provider 无关。Cloud PR [#324](https://github.com/felinics/Memoh-Cloud/pull/324) 在同步这套实现时发现它；修复先在 OSS 完成，Cloud 再同步并验证其租户与 E2B 边界。

## 当前补丁的目标与实现

安全条件：**查询失败不代表没有引用；未完成的清理必须保留恢复依据。**

1. 从数据库读取该 App 的持久化引用，与本次发布的 release 比较，得到待清理项。新旧 release 相同也不能直接认为清理已经完成。
2. 开始清理前，完成所需的依赖和连接器共享引用查询。只有需要处理的资源才查询对应领域；全部保留的 release 不需要额外工作区探测。
3. 对没有其他 App 引用的依赖，要求工作区正在运行、探测成功、依赖已知且没有进行中的操作。无法确认时保留引用并报错。
4. 被其他 App 引用的资源只解除当前 App 的引用；需要物理删除的资源先执行删除，确认成功后再删除引用。外部调用或引用写入失败就停止，保留该项及后续未处理引用。
5. 清理属于 materialize 的完成条件，Install、Resume 和 Update 共用此逻辑。错误通过已有错误事件返回，并持久化为 `failed` 与 `last_error`；成功事件仅在清理之后发送。
6. 重试重新读取持久化引用。新服务实例也能从现有记录继续，不依赖首次请求中的旧引用切片。已确认不存在的依赖可以补删引用，无须重复执行卸载脚本。

本次使用现有表、状态和事件，没有新增迁移、API 字段或后台服务。使用已有 `failed` 表示发布后的清理失败，意味着 Skills 可能已经是新版本；这里没有承诺整个 App 更新具备原子回滚。

## 从 Nix 借鉴的部分

- [GC roots](https://nix.dev/manual/nix/2.34/package-management/garbage-collector-roots)：资源是否保留取决于明确的引用关系。当前补丁保留未完成的引用，避免丢失清理依据。
- [删除前事务检查](https://github.com/NixOS/nix/blob/d262d70a49e3e303151831cf268a7241abe85ae0/src/libstore/local-store.cc#L1416-L1439)：取得完整、可信的引用信息是删除的前提。当前补丁先修正查询错误语义，尚未实现 Nix 的事务删除保护。
- [临时 roots 与删除同步](https://github.com/NixOS/nix/blob/d262d70a49e3e303151831cf268a7241abe85ae0/src/libstore/gc.cc#L84-L158)：安装过程也要保护资源。后续需要让新增引用和删除经过同一个协调入口。

Nix 使用本地 store、SQLite、文件锁和 socket。Memoh 包含远端工作区和第三方连接器，应借鉴保护条件与恢复机制，不能把本地锁直接当成跨 Server 的删除协议。

## 本次未解决的边界

- **跨 App、跨 Server 的引用竞态仍然存在。** 当前锁只覆盖一个 App，预读共享引用不是并发删除权。A 预读后 B 新增引用的窗口，需要后续资源级协议修复。
- 完整的 App 卸载 `Remove` 路径仍有组件失败后删除安装记录的独立问题，本补丁只处理发布/更新后的旧引用清理。
- 现有 Upsert 仍提前记录目标 release。重试失败状态会重新 materialize，但尚未分离目标版本、已发布版本和回滚版本。
- 用户主动安装、已启用 Agent、依赖之间的传递关系，应分别明确是否构成保留根。当前补丁仍采用已有 App 引用和来源判断，不改变资源所有权产品规则。
- 连接器解绑与整个 Bot 的账号断开需要明确产品语义。本次保持既有删除策略，仅修正错误处理和恢复。
- 外部调用成功、数据库确认失败时可能重试删除；依赖探测和连接器已有 NotFound 处理支持部分恢复，但不构成跨系统 exactly-once 保证。

## 后续路线

### 1. 统一资源引用和删除协调（OSS）

定义依赖的 `(team, bot, workspace_target, dependency)` 与连接器的 `(team, bot, connection_id)` 资源标识。仓储层在短事务中检查保留根/引用/安装占用并取得删除 claim。新增引用也必须经过该入口，遇到 `deleting` 应等待或返回可重试冲突。

将数据库协调与外部执行分开。脚本和第三方 API 在事务外运行，带持久化操作标识；成功后确认完成。结果未知时保留 claim 并核对真实状态，不能仅按超时接管，以免旧执行继续删除新资源。检查所有安装、恢复、更新、卸载和连接器授权入口，避免只保护删除端。

### 2. 明确保留根与发布状态（OSS）

评估用户主动保留、Agent 所需依赖、传递依赖和安装中占用；资源无人引用后进入可回收状态。评估目标 release 与已发布 release 分离，以及按版本保留文件的发布/回滚流程。独立清理执行器可以复用服务生命周期，不要求引入新的服务或 broker。

### 3. Cloud 同步与验收

OSS 修复合并后同步到 #324，保持 Team 上下文、RLS 和 provider-neutral workspace client。若后续增加迁移，按 Cloud 已占用编号调整并重新生成 SQLC。Submodule PR 合并后由已有 Action 更新外层 gitlink。

真实验收覆盖两 Team、两个 workspace target、E2B 暂停/恢复、Server 中断、连接器断开失败和重试。Cloud 专属执行和隔离测试不能替代 OSS 的资源生命周期回归。

## 验证要求

- 查询自身引用或共享引用失败时，零资源删除且恢复引用保留；恢复后仍保护另一个 App 的引用。
- 外部删除或删除引用失败时，操作失败且没有提前的 `done`；重建服务实例后可以继续。
- 工作区不可用、探测失败、依赖未知或正在操作时，不依据不完整信息清理。
- 同版本 Update、UpdateSelection 重试和 Resume 均能处理残留引用。
- 成功清理后只有一个最终 `done`，失败路径没有 `done`。

这些是服务层故障注入要求，不代表已经完成真实工作区、第三方授权或人工 QA。资源级并发协议完成时还必须加入确定性并发和数据库集成测试。
