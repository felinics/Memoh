# Phase 3：Team共享知识库

> 前置阅读：[README.md](./README.md)
> 依赖：无。**Wiki与Group解耦**（决策D3），本阶段不依赖Phase 1，可与之完全并行。

## 1. 目标

为每个Team提供**一份**共享知识库，**人和Agent都是一等使用者**（决策D11）。它承担三件事：

1. 团队的结构化知识沉淀（文档、看板）
2. Bot之间产物交接的载体（见第6节）
3. Inbox的事件源（Phase 4）

这块投入不小，但它是Agent Team中唯一的共享底座——共享工作空间已被排除（README第5节），Wiki必须补上它留下的缺口。

## 2. 存储分层

**结构化数据存Postgres，正文与附件blob走storage provider抽象**（决策D12）。

不要把结构塞进对象存储的key前缀。文档树、Issue状态、评论、提及、版本、引用关系全是关系数据；放进key前缀后，列目录、改标题、移动子树、按权限过滤、按assignee查Issue都会退化成全桶扫描。

| 层 | 内容 | 落点 |
| --- | --- | --- |
| 结构 | 节点树、元数据、评论、提及、版本指针、引用 | Postgres |
| 内容 | Markdown正文、附件二进制 | storage provider |

现有`internal/storage/providers/`只有`localfs`、`containerfs`、`fallback`。**S3是新增的provider实现，默认仍为localfs**，不得把S3写死进Wiki的领域模型——自部署用户不一定愿意运行MinIO。

### 2.1 内容寻址的取舍

`internal/media/`是内容寻址的，跨Group会天然去重。这带来两个后果：

- 删除语义变绕：G1删除了某文件，但G2仍在引用同一blob。
- 构成一个很弱的存在性侧信道。

大多数产品接受「blob去重＋元数据层做权限」，本设计也采用该方案。但这必须是有意识的选择，不能是无意中变成这样的。

## 3. 数据模型

范围收敛到四类实体：

| 实体 | 说明 |
| --- | --- |
| node | 知识库节点。`type`区分`doc`与`issue`；`issue`额外携带status、assignee等字段 |
| comment | 挂在节点上的评论 |
| mention | 从正文或评论中解析出的@提及，指向用户或Bot |
| attachment | 节点的附件，指向blob |

要点：

- 节点树用父子引用表达，支持移动子树。
- `wiki_nodes`只携带`team_id`，**不携带`group_id`**（决策D3）。遵循README第8.4节的表约定。
- **Issue是节点的一个type**，不是独立子系统。看板视图是对`type=issue`节点按status的投影。
- 版本：每次修改保留版本记录，用于审计与回滚（第8节）。

### 3.1 预留列：`visibility_group_id`

`wiki_nodes`上预留一个**可空**的`visibility_group_id`，默认NULL表示Team内全员可见。

**Phase 3不实现任何基于该列的逻辑**，全部查询按「NULL＝可见」处理。留它的理由与`group_bot_members.allow_inbound_contact`相同：将来若某棵子树需要收紧到特定Group，有列在是改代码；列不在则是一次迁移加全表回填，而Wiki是本方案中数据量最大的部分。

这是零成本对冲，不是隐藏的功能开关。任何实现都不得提前消费它。

## 4. 权限

**读：Team内全部成员（人与Bot）可读全部内容，不做访问控制**（决策D13）。

这是本阶段唯一的实质取舍，必须被明确理解并接受：

> Wiki不是保密载体。敏感内容不放Wiki。

它换来的是UX上的彻底简化——不需要选组、不需要理解「这篇文档属于谁」、不需要在切换Group时重新定位、不存在跨组引用被拒绝的困惑。Group与Wiki解耦的动机正在于此。

**写：由Bot自身的设置控制。** 「某个Bot是否允许写Wiki」是`bots`上的一个设置，不是Group成员关系上的属性——一个面向外部客户的Bot大概率不应该能写入内部知识库，而这与它属于哪个组无关。人类的写权限沿用既有的账号角色体系。

其他规则：

- 不存在跨Group引用的概念，因此也不需要禁止。全库是一棵树。
- Wiki工具的注册条件是「该Bot允许访问Wiki」，与Group成员关系无关。Bot不属于任何Group时，Wiki工具**照常注册**。

### 4.1 与Group的组织性关联（约定，非机制）

创建Group时，可以在Wiki中自动建立一个同名顶层目录。

这**纯粹是组织约定，不带任何权限含义**：任何人和任何Bot都能读写它，内容也可以放在树的任何其他位置。它的作用只是让「每个组有自己的地盘」这个直觉有个落点，而不引入一丝访问控制的复杂度。

实现上不得因此在Wiki的任何查询路径中引用Group表（见`01-group.md`验收项GRP-004）。

## 5. Agent工具集

不要提供「读取整个Wiki」的工具。工具集应为：

| 工具 | 说明 |
| --- | --- |
| 搜索 | 语义＋关键词。可复用`internal/memory/`已有的Qdrant与BM25基础设施 |
| 按路径读取 | 读单个节点 |
| 局部编辑 | 见第5.1节 |
| 创建节点 | 在指定父节点下新建。无需指定group |
| 评论 | 在节点上发表评论，可@他人 |
| 附件发布与拉取 | 见第6节 |

### 5.1 并发写必须有冲突检测

Agent是会并行的。整篇覆写在并发下必然互相踩，因此**必须**具备下列之一：

- 乐观锁：读取时返回version或etag，写入时校验；冲突则返回给Agent，由它重读再改。
- Anchor级patch：只提交局部改动与其锚点。

这一点的重要性高于表面观感——它是Wiki能否被多个Agent同时使用的前提。

## 6. 附件交换：共享工作空间的替代

共享工作空间被排除后，「Bot A产出一个文件给Bot B使用」这个需求失去了载体。Wiki必须补上，因此需要一对工具：

- 把workspace中的文件发布到Wiki（作为节点附件）
- 把Wiki附件拉取进自己的workspace

没有这两个，Bot之间就只能靠A2A传纯文本，稍大的产物无法交接。**这是排除共享工作空间之后必须补齐的最小闭环**，不是可选增强。

## 7. 与长期记忆的边界

这是最容易职责重叠的地方，必须划死：

| | Wiki | 长期记忆（`internal/memory/`） |
| --- | --- | --- |
| 可见性 | 显式、人可读 | 隐式 |
| 编辑 | 人和Agent都能改 | 自动抽取 |
| 归属 | Group共享 | per-bot（决策D5） |
| 审计 | 有 | 无 |

规则：

- **记忆不自动写入Wiki。** 否则Bot会把私有记忆泄漏到共享空间。
- Wiki可以作为记忆检索的一个可选来源。

不划清楚的后果是：同一份事实在多个Bot的私有记忆中各存一份互相矛盾的副本。

## 8. 审计与回滚

Agent修改Wiki必须留痕：谁改的、哪个Session改的、diff是什么。人类必须能回滚到任意历史版本。

这是信任的前提。没有它，人类无法放心让Agent写入共享空间。

## 9. 明确不做的事

| 不做 | 原因 |
| --- | --- |
| block级富文本编辑器 | 工作量以月计，与Agent协同主线无关 |
| 实时协同编辑（CRDT） | 同上。并发问题由第5.1节的乐观锁解决 |
| 独立的Issue子系统 | Issue是node的一个type |
| 按Group划分Wiki | 认知负担大于收益，见第4节与README第5节 |
| 节点级访问控制 | 同上。只预留`visibility_group_id`列，不实现逻辑（第3.1节） |
| 把结构存进对象存储 | 第2节 |

## 10. 验收要求

### WIKI-001：结构与内容分层

- 列目录、移动子树、改标题必须是Postgres上的操作，不得触发对象存储的遍历。
- 更换storage provider（localfs↔S3）不得影响结构层行为。
- 默认配置下不依赖S3。

### WIKI-002：权限与Group无耦合

- Team内任意用户与任意Bot都必须能读取全部节点。
- 用户切换当前Group时，Wiki的可见内容必须不发生变化。
- Wiki的任何读写路径都不得引用Group表；`visibility_group_id`必须始终为NULL且不被任何查询消费。
- 未被授予Wiki写权限的Bot发起写操作必须被拒绝。

### WIKI-003：并发写

- 两个Agent基于同一版本并发修改同一节点时，后提交者必须收到冲突而不是静默覆盖。
- 冲突返回给Agent的信息必须足以让它重读并重试。

### WIKI-004：附件交换

- Bot必须能把自己workspace中的文件发布为Wiki附件。
- 另一个有权限的Bot必须能把该附件拉取进自己的workspace。

### WIKI-005：审计

- 每次由Agent发起的修改必须记录发起Bot与Session。
- 必须能查看任意两个版本之间的diff，并回滚到指定版本。

### WIKI-006：记忆边界

- 记忆抽取流程必须不会写入Wiki。
- 该项需要有测试守卫，而不仅是约定。
